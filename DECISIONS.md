# KiCode Architecture Decision Records (ADRs)

## ADR-001: Modern AI Chat Interface & Interactive Elements
- **Context**: The TUI needed to provide a modern, engaging AI coding interface while maintaining exact terminal row layout geometry.
- **Decision**: Added "Where should we begin?" greeting to home screen, created a rounded input prompt layout with `+` attachment launcher, `[Image i]` chips, `🧠 Think` reasoning pill, and `↑` send button.

## ADR-004: Emoji-Free Bar-Style Chat Area
- **Context**: The prompt box used emoji (`🧠`, `⚡`, `📋`, `◆`) and a framed `╭╮╰╯` border that competed with the transcript's own rules; sender `You`/`Ki` header rows cost a row on every turn.
- **Decision**: The box is now a single accent `▌` bar (no top/bottom border, bar-only padding rows), plain `[Think]` pill and `↑` send button, `▌ Build · model · variant` status row with single separators, `┌┐└┘` picker corners, `│` tool rule, and no sender headers — answers are plain prose, requests are filled blocks.
- **Outcome**: All 823 tests pass; the layout matches the VS Code-style reference (separator, accent bar, `Ask anything...`, status row, path + `ctrl+p commands` footer).

## ADR-005: Airy Tabs with +NEW and Home on Every Fresh Session
- **Context**: The tab close box sat tight against the title (easy to miss, hard to click) and the `+ New session` button ate a wide row; worse, `/new` pushed a `new session` transcript entry, so a fresh session opened on a one-line transcript instead of the home screen.
- **Decision**: Each tab is now ` title  ×  ` (two cells of air around `×`, which is also the click target), the trailing button is a compact accent `+NEW`, and `newSession()` reports via the state-row notice instead of a transcript note — so `entries` stays empty and every new session opens on `Where should we begin?`.
- **Outcome**: All 823 tests pass (tab geometry tests re-pinned; `/new` test now also asserts the home greeting).

## ADR-006: Palette Lists Only Runnable Commands
- **Context**: The `/` palette showed the whole OpenCode catalogue — aliases (`/q`, `/open`, `/project(s)`, `/resume`, `/effort`, `/thinking`) as separate rows and names KiCode cannot run (`/agents`, `/pair`, `/plugins`, …) as dimmed rows — tripling the visual noise of choosing a command.
- **Decision**: `filterCommands` returns only available, non-alias commands. The full `COMMANDS` catalogue stays as the single source of truth for the dispatcher, so typed aliases still run and typed dead names still explain why they cannot — they just no longer occupy rows in the list. `/help` already filtered the same way.
- **Outcome**: All 823 tests pass (palette tests re-pinned to open on `/btw`; new test pins that aliases and dead names are absent from the list but present in the catalogue).

## ADR-007: Plan + Todo Session Tools
- **Context**: Plan mode only subtracted — it refused `write`/`edit`/`bash` but offered no deliverable, so a plan was prose the user had to hunt for and multi-step work had no memory across turns.
- **Decision**: New `plan` tool (goal + numbered steps with optional detail/files, presented once for review; calling again replaces it) and `todo` tool (`add`/`done`/`list`/`clear` over a numbered session list), sharing per-agent closure state so sessions never leak into each other. Both registered always and never approval-gated (in-memory only); `PLAN_MODE_PROMPT` now names them as the plan-mode deliverable.
- **Outcome**: All 834 tests pass (11 new in `plan.test.ts`).
- **Outcome**: All 117 layout and rendering tests pass with pixel-perfect caret and row coordinates.

## ADR-002: Mouse Text Selection & Clipboard Protocol
- **Context**: Automatic copy and paste on text selection caused accidental clipboard pollution and unintended input insertion.
- **Decision**: Decoupled mouse selection from clipboard mutation. Mouse drag highlights transcript text without mutating clipboard or prompt buffer. `Ctrl+C` explicitly copies the selected range. Right-click opens a context menu with separate options for text paste, image paste, and transcript copying.
- **Outcome**: Clean, intentional text copy/paste UX matching desktop standards.

## ADR-008: Compact at 100K, Remember While Working, Hermes Optional
- **Context**: Sessions on free-tier windows die past ~100K tokens while the configured 128K window says there is room; learnings evaporated at session end, which was the whole case for bolting on the Hermes agent runtime; and every new save prompt would train the user to stop saving.
- **Decision**: (1) `compaction.compactAt` (default 100,000, `KICODE_COMPACT_AT`, persisted by `--init` when changed) caps the auto-compact budget below the window — `shouldCompact` uses `min(window − reserve, compactAt)`, so a wider window never delays the cut. (2) A `remember` tool (`skill` → `skills/<slug>/SKILL.md`, never overwriting; `memory` → dated append to `memories/projects/<slug>.md`) is always registered and deliberately not approval-gated; safety is positional (brain directory only, slug names, 12K/4K caps, secret shapes refused, plan mode refuses). The model is prompted to save verified, reusable learnings and announce each save in one sentence. (3) With the local brain learning on its own, the Hermes agent runtime is parked as an optional future (M13/M14 stay on the roadmap, unbuilt) — not a requirement.
- **Outcome**: All 868 tests pass (15 new: 3 compactAt budget cases, config env/file defaults, `--init` persistence, 10 remember cases covering no-overwrite, slug jailing, secret refusal, truncation).

## ADR-009: Permission Prompt Floats Centered
- **Context**: The approval modal sat where the prompt box had been — bottom of the screen, full width — while the eye is in the middle of the transcript it is being asked about.
- **Decision**: `renderFrame` overlays the modal as a 72-wide card centered over the transcript (`paint` with a panel background on the page background), keeping the tab bar and footer visible. The prompt box and caret stay hidden while the modal owns the keyboard; the state row keeps its warn edge, and the card carries no click targets — a click still cannot answer it.
- **Outcome**: All 870 tests pass (2 new pinning the centered row and the visible tab bar/footer; 4 existing modal tests re-pinned to the prompt staying hidden).

## ADR-010: Sessions Picker Shows When + How Long, Searches the Preview
- **Context**: `/sessions` rows carried only title + id — fifty sessions of `new session` are indistinguishable, and searching matched the 28-char title at best. The store already knew more (date, length, model, opening request).
- **Decision**: `SessionSummary` gains optional `updatedAt`/`messageCount`/`model`/`preview` (run.ts maps them from the record; `sessionPreview` flattens and caps the opening request at 100 chars). Rows show `today · 4 msgs` as trailing metadata; preview + model travel as non-displayed `keywords` that `filterPickItems` matches, so typing a word from the opening request finds the session without snippets drowning the titles.
- **Outcome**: All 874 tests pass (4 new: preview flatten/cap/empty, keyword matching, picker trailing + preview search + switch).

## ADR-011: Centered Modal Pickers, In-Input Docked Clipboard Menu & Turn Queuing/Pause
- **Context**: Modal dialogs and pickers were left-top aligned, context menus replaced the transcript body rather than anchoring to the input area, clipboard content lacked visual inspection (making pasted images or multi-line text opaque to the user), and users could not push questions in between conversation turns or request an immediate pause.
- **Decision**:
  1. Centered all modal picker dialogs (`renderPicker`) vertically (`topPad = Math.max(Math.floor((height - out.length) / 2), 0)`) and offset all hit targets so mouse clicking aligns exactly.
  2. Anchored the right-click context menu directly into the chat input area docked above the prompt (`renderBottom`), preventing transcript obliteration.
  3. Added clipboard real content previews in `clipboard.ts`: 16x4 24-bit ANSI RGB colored block grid (`█`) by decompressing PNG IDAT scanlines via `node:zlib` for images, and line-numbered text preview for string clipboards.
  4. Added turn queueing and pausing (`/queue <msg>`, `/insert <msg>`, `queue: <msg>`, and `"pause"` / `"/pause"`). If the model or turn is busy and user types "pause", it cancels the active turn and marks `isPaused = true` (`▌ paused`). The agent system prompt is instructed to pause immediately on pause requests. Queued messages are automatically dispatched in order upon completion or unpausing.
- **Outcome**: All 874 tests pass across 46 test suites; clean production build.

## ADR-012: Reading-Level Transcript Discipline (Selection Fill, Thinking Ticker, One-Line Results, Folded Notes, Ask Summaries)
- **Context**: Four reading problems compounded each other. (1) The selection highlight used inverse video (`ESC[7m`), which several terminals render invisibly. (2) A live reasoning stream printed every delta, turning the transcript into a scrolling wall while the model thought. (3) At medium verbosity a tool result still printed up to 12 lines mid-turn, when nobody is reading output — they are reading what the tool touched. (4) Repeated identical failure notes (a free gateway 429ing every retry) stacked identical blocks down the transcript, and `ask` tool calls dumped their whole question objects — headers, option lists, descriptions — as raw JSON, which both flooded the transcript and made the centered permission modal (ADR-009) appear to collide with text.
- **Decision**:
  1. `theme` gains `Styles.selection` (accent background, background foreground) and `ansi.markCells` takes the highlight style as a parameter, replacing span styles inside the range instead of prefixing inverse video. The modal box is selectable like every other row.
  2. While reasoning is open and verbosity is low/medium, the transcript renders one ticker line: `▌ thinking <newest sentence>` (accent + faint), where the newest sentence fragment is capped at 96 chars. High verbosity keeps the full stream; closed thoughts still show `Thought: Xs`.
  3. `resultLines` at medium verbosity summarizes a non-error result to its first line plus `· N lines`; low and high keep their previous behavior.
  4. `summarizeArgs` takes the tool name: `ask` renders as `3 questions: "<first question>"`; every argument value is capped at 96 chars, so one long `content` cannot flood the line. Applies to the transcript, copied/exported text, and `/diff` change labels.
  5. Identical notes fold into one row that admits the count (`[Provider rate-limited the request (HTTP 429) ×3]`). Turn-failure notes fold past the user's retry message; strictly consecutive notes fold regardless. The count rides on the note entry, so exports show it too.
- **Outcome**: 910 tests pass across 47 files (selection, ticker, fragment, result, ask-summary, value-cap, note-fold, and a live mouse-drag case added); typecheck and ESM build clean. The permission modal now floats over a readable transcript rather than a JSON wall. Found while verifying live: the drag highlight was fully implemented and tested at the frame level but `TuiApp.state()` never handed `this.selection` to the renderer, so it never appeared on screen — the new regression test drives a real SGR mouse drag through the input loop and asserts the raw frame bytes carry the accent fill and no inverse video.

## ADR-013: Rate-Limit Recovery — Backoff Before Switching, Auto Free→Free Chain, All-Capped Summary
- **Context**: TokenHarbor's free routes 429 frequently ("free-model rate limit reached; slow down and retry"). With no fallbacks configured the turn died on the first 429; even with a chain, hops fired back-to-back into the same busy gateway, and a single-route session had nowhere to go at all. The owner asked for "something done about the rate limiting".
- **Decision**:
  1. A 429 pauses before the next route. The gateway's own `Retry-After` (via the quota reading) is honoured up to a 60 s ceiling; without one, 1.5 s growing one step per hop already tried. The pause emits a `route-wait` stream event so the busy row reads `rate-limited on <route> — waiting Ns…` instead of the UI looking hung, and it is sliced (250 ms poll) so Ctrl+C lands within a quarter second. The transcript deliberately keeps no entry — a wait is seconds, not history.
  2. When the session's model is free and no explicit fallbacks are declared, the chain is extended the first time it runs dry: the endpoint's own `/models` list is fetched once, other free models become hops (capped at 4, same endpoint and key, de-duplicated against the chain). Never a paid model — a paid fallback silently changes the quality of every answer after it. Discovery failure contributes nothing; the real error is what the user sees. **Opt-in only** (ADR-015 made the recovery modal the default path): `"fallbackAuto": true` in `kicode.json` or `KICODE_FALLBACK_AUTO=on`.
  3. A chain that ended only in rate limits throws a different error from one that failed otherwise: "Every route is rate-limited — … wait a bit and send again, or /models to pick another route."
- **Outcome**: 937 tests pass across 48 suites (backoff/cap/no-pause-for-502, discovery append/dedup/failure, capped summary; plan-mode classifier also permits the stderr-quieting idioms `2>/dev/null`, `2>&1`, `1>/dev/null` that models use constantly while exploring — a redirect to a real path is still refused). Typecheck and ESM build clean.

## ADR-014: `/attach` — Files from the Prompt, Two Ways Across
- **Context**: The prompt accepted pasted screenshots and `@file` mentions, but nothing in between: a user mid-sentence who wanted to show the model a screenshot on disk or a spec document had no way to hand it over, and free models silently drop image parts entirely.
- **Decision**:
  1. `/attach <path>` reads at attach time, not send time — a bad path is a message while the user can still retype it. Relative paths resolve against the session's cwd; quoted paths are unquoted.
  2. Images (`png/jpg/webp/gif`, ≤8 MB) join `attached` and ride the existing pasted-screenshot base64 path, badges and all — visible to vision-capable models, dropped by the rest.
  3. Everything else (≤512 KB, decoded as text, binary refused, content capped at 24 000 characters with the truncation named in the block) becomes a named `Context from attached file "…"` block appended to the turn's words — the same shape an `@file` mention produces, so every model including the free ones reads it without any provider content-part changes.
  4. The typing area shows `[name]` badges beside the image chips; backspace on an empty prompt detaches the newest attachment of either kind; the right-click menu clears images or documents separately. Queueing (`/queue`, `/insert`) carries attached documents like images.
- **Outcome**: 937 tests pass (attach resolution, mime mapping, caps, binary/missing/directory refusals, doc blocks, badge rendering, two live end-to-end attach flows through the input loop); typecheck and ESM build clean. The command palette gained `/attach`, shifting palette order — the two tests that pinned row positions were re-pinned.

## ADR-015: The Recovery Modal — a Failed Turn Is a Question, Not a Verdict
- **Context**: ADR-013 recovered rate limits inside the router, but the owner asked for the choice to be visible and theirs: when a model is rate-limited or errors, a modal should pop up in the chat area with the message and the option to choose a new model, instead of the app deciding on its own. Auto-switching also had a cost the owner could not see: the model answering silently changed mid-session.
- **Decision**:
  1. A failed turn (any non-cancelled error out of `agent.send`) leaves the error note in the transcript **and** raises a centered modal: the gateway's message as the body, `r retry · m choose model · esc dismiss` as the options. Goal runs are exempt — a modal nobody is watching would stall an autonomous run, so they keep the note only.
  2. `r` re-runs the exact request — same expanded words, same attachments, same model — because a rate limit is usually about *when*, not *what*. `m` opens the existing model picker with the failed turn set aside; the model that lands (a move or a re-confirm of the current one) is the one the retry runs on. Esc keeps the error and dismisses. Ctrl+C is deliberately not owned by the modal, so quit means quit.
  3. The queue holds while the modal is up (a turn running behind the question would be a second thing deciding what the screen is doing) and moves when it is answered. The modal's own failure path — the picker never opened — hands the decision back rather than dropping the turn.
  4. `fallbackAuto` flipped to **off by default**: the modal is the recovery path; the ADR-013 chain remains for those who ask for it (`"fallbackAuto": true` / `KICODE_FALLBACK_AUTO=on`). The 429 pause now only fires when a route is actually next, so a dead-end failure reaches the modal instantly.
- **Outcome**: 940 tests pass across 48 suites (modal on a rate-limited turn, `r` retry re-sending the exact prompt, `m` → picker → model move → retry, Esc dismissal, the note-fold flow updated to dismiss between turns). Typecheck and ESM build clean. Gotcha: a lone Esc is flushed after ~40 ms as a possible escape sequence — tests asserting on the post-Esc frame must tick past that.

## ADR-016: The Attach Button Replaces `/attach`, and the Caret Row Bug It Found
- **Context**: The owner asked to drop the `/attach <path>` slash command and make attaching a click: an attachment icon on the right of the input area that opens the platform's own file-selection window and attaches whatever is chosen. A terminal cannot raise an OS dialog by itself, so the picker has to be delegated to a tool the machine already ships (the zero-dependency rule forbids an npm dialog package) — and the moment the button existed, its tests exposed a real UI bug that had been invisible: the prompt-row caret row was computed without the tab bar's offset.
- **Decision**:
  1. `src/pickFile.ts` opens the platform's dialog through system programs only: PowerShell's `System.Windows.Forms.OpenFileDialog` on Windows (filtered to images + documents, `CheckFileExists`), `zenity --file-selection` on Linux with `kdialog` as a fallback, `osascript`'s `choose file` on macOS. Cancelling, a missing tool and an unknown platform all resolve `null` silently — a closed window is "never mind", not an error — and every outcome flows through one injectable runner so parsing and cancellation are unit-testable without a dialog. A file-type filter on Windows keeps the picker from opening on `*.*` as the whole answer.
  2. The `[+]` button is drawn on the **right** of the input bar, beside the `↑` send button. The click handler mirrors the draw arithmetic exactly (the geometry lives in two files, so both were changed together), and the new tests locate the button by reading the drawn frame rather than hardcoding a column. **Amended after review**: the `[Think]` variant pill that used to sit between them was removed at the owner's request — the prompt row now carries only the two controls pressed while typing (`[+]` and `↑`), the variant is changed with `/effort`, and a frame test pins that `[Think]` is gone from the row.
  3. A click calls the injected `options.pickFile` (wired in `run.ts`), and the chosen path lands in the machinery `/attach` already used: images into `attached`, text into `attachedDocs`, badges, backspace-detach and the right-click clear items all unchanged. Where no picker exists (a platform with no tool, or a test), the click falls back to the prompt-input box asking to type or paste a path, so the button is never a dead click. `/attach` is gone from the catalogue and the dispatcher; `attachFile(path)` stays as the internal landing place.
  4. **Bug found and fixed while testing the button**: `renderFrame` computed the caret row as `1 + bodyRows + bottom.caretRow`, omitting the tab bar's row. Whenever the sidebar was visible every prompt-row click, drag and the terminal caret itself sat one row too high — the caret landed on the state row. It is now `1 + tabRowCount + bodyRows + bottom.caretRow`. A second, quieter consequence was pinned too: a drag that started on the chrome under the rule copied `Ask anything...` as if it were the conversation, so the selection-start guard now refuses rows at or below `promptRow - 2` (the rule).
- **Outcome**: 948 tests pass across 49 suites (two consecutive green runs), typecheck and ESM build clean (`dist/cli.js` ≈ 456 KB). New coverage: 6 picker unit tests (path parsing per platform, zenity→kdialog fall-through, cancel, unknown platform, unquoting) and 3 live input-loop tests — picker → badge → context block in the sent prompt, a cancelled dialog leaving the prompt untouched, a bad path reported, and the no-picker fallback asking for a path in the prompt. The two frame tests that encoded the caret off-by-one were corrected to row 21 of a 24-row frame (matching the sibling test that already said the input sits there), and the palette-order tests shifted back one row for the removed command.

## ADR-017: Panels Float Over the Page, and the Page Steps Back
- **Context**: The owner's words: *"all the modal or tools opening like /models, /settings etc. must open in modal and when opening make the background as grey or less visible or fade"*, and then *"make the model switching modal come near the chatbox and with the background fade, means only focus area is modal"*. Until now a picker or a menu **replaced** the transcript — `renderBody` returned the panel instead of the conversation, so the rows behind it went blank — and a picker card was centred in whatever room was left. That made `/models` read as a different screen rather than a question asked over the screen you were already reading.
- **Decision**:
  1. A picker or a menu is now a **card laid over the page, not instead of it**. `renderFrame` renders the body twice when one is up: once with the panel taken out (the page) and once as the panel itself (the card). A card row that carries text covers the page row; the card's own blank padding rows let the page show through around it. The card therefore keeps its floating shape while the conversation stays where it was.
  2. Every page row the card does not cover is **faded**: one faint style on the page background (`fadeRow`). Chip fills go too — a block of colour left at full strength behind a card reads as a second panel, which is the opposite of "only the focus area is the card". The permission modal gets the same treatment, so a prompt floats over a dimmed transcript rather than over a bright one.
  3. The fade stops at the rule. The mode row and the footer keep their colours: they are the input area's own chrome, the permission card is deliberately one box with the state row under it, and dimming the footer would dim the very keys the card is asking the user to press.
  4. The card is drawn at the **foot of the page** — `topPad = height - out.length`, was a vertical centring — so a picker lands directly above the rule and the prompt, where the eye already is while typing. The full-screen menu (band) is bottom-anchored the same way, with its hit rows shifted by the padding the change added.
  5. While a card is up it **owns the clicks**: `panelRows` takes the card's hits only, because a row you cannot see clearly is not a row you should be able to press.
- **Outcome**: 952 tests pass across 49 suites, typecheck clean, ESM build ≈457 KB. Three frame tests pin the new behaviour: the card's lower edge is exactly one row above the rule, the conversation behind it is on screen but faint (and back on the page background), and the only click targets are the card's own rows. Note for later: the question panel (`ask`) still replaces the page rather than floating over it — it is a multi-step form that owns the screen, and its own test pins that.

## ADR-018: The Input Box Is the Typing Area, and the Todo List Goes Live
- **Context**: The owner sent screenshots of the input bar with three asks — *"remove the arrow at the right side of the chatbox"*, *"add background colour to this chatbox, to understand this is typing area"*, *"also add padding between the texts"* — and, in the same breath, *"show live todo progress in the transcript while the agent works"* and *"make the chat area background deeper"*. The row carried two controls where only one was ever clicked; the box was filled with `panel`, which is also the tab bar's fill and sits barely a shade off the page, so on the owner's screen the input area read as more transcript; the `Ask anything...` placeholder and the `Build · model · variant` row were stacked flush; and the `todo` tool printed a fresh copy of its checklist on every call, so a five-step task buried the conversation under near-identical blocks.
- **Decision**:
  1. **Send has no button.** The blue `↑` was the loudest thing on a quiet row for the one action the keyboard already has (enter); `[+]` is now the row's only control, anchored to the right edge. `app.ts`'s hit box was re-derived with it — `attachStart = usable - attachLen - 1`, the drawn glyph and the hit box computed from the same arithmetic in two files — and the attach tests read the button's column off the drawn frame, so they validate the pair rather than a number typed twice. `styles.sendButton` is gone from the theme.
  2. **The box is drawn on `theme.block`** — the fill a user's own turn sits on — so the place being typed into is visibly the same material as the words it becomes. `panel` stays the tab bar's and a card's fill; the permission card keeps it, and the state row takes whatever surface is over it: the card's `panel` while a decision is up, the box while there is one to type into, the page otherwise.
  3. **The page behind it got deeper.** The `kicode` background is `#08090f` (was `#0c0d14`) — the near-black the palette is documented as being built around — which is what turns the box into a raised surface rather than a slightly different transcript row. Only the default theme's page moved; the light half of the roster stays light.
  4. **A blank row of the box's own fill sits between the editor and the state row**, and it *replaces* the padding row that used to trail under the status line rather than being added to it. A fifth row would have cost the transcript one of its 24 and pushed a four-entry conversation straight into a scrollbar — which the suite caught immediately, because the scrollbar's glyph landed on the blank separator rows the spacing tests count. Same height, different distribution.
  5. **The todo card is live.** A `todo` tool result no longer appends: the previous card is spliced out and the new state pushed at the end, so there is exactly one checklist, always at the tail — where the work is — instead of frozen where the list was first written. The system prompt gained one rule asking for a list whenever work spans several steps; a tool the model never calls has no progress to show.
- **Outcome**: 955 tests pass across 49 suites (two consecutive green runs), typecheck clean, ESM build 457.37 KB. New coverage: a frame test pinning the box as one `block`-filled surface with its padding rows included, a frame test pinning the editor and the state row two rows apart with the bar between them, the prompt-row test re-pinned (`↑` absent, `[+]` present), and two transcript tests — one card rewritten in place and moved to the end, every other tool's output still logged. Test-maintenance note: five frame tests used `frame.lines.filter((line) => line.includes(block))` to find a *turn's* block, which the filled input box now also matches; they were given a `transcriptOf(frame)` helper that slices above the input rule — which is what they always meant. The caret-row and mouse-drag assertions stay at row 21: the box is the same height as before.

## ADR-019: The Card Answers to a Mouse, and Escape Is a Chip
- **Context**: The owner sent a screenshot of the recovery card — *"The turn failed — what now?"* with `r retry · m choose model · esc dismiss` — floating in the middle of the screen, and asked: *"i want this modal come near the input box and make it clickable using mouse. not only that we need all the action can be doable using mouse, also add [x] to all esc actions."* The card was deliberately the one thing a mouse could **not** answer (ADR-009: *"a click still cannot answer it — the box carries no click targets, by design"*), its decision row was a single string, and every card in the app printed `esc` as a word: readable, and unreachable without a keyboard.
- **Decision**:
  1. **The card comes to the input box.** Its last row is now the last row of the conversation — `start = pageRows - box.length`, which was a vertical centring — so it lands directly above the rule and the prompt, exactly where a picker lands (ADR-017) and where the eye already is while typing. The fade behind it is unchanged.
  2. **`Modal.options: string` became structure**: an optional `question` (`allow?`), a `choices` list of `{ key, label }`, and an optional `footer` of key/label pairs for the keys the card itself does not name — so the card and the session footer together name every key exactly once. The permission card offers `[y] yes · [a] always · [n] no` and leaves `esc deny · ctrl+c deny + stop` to the footer; the recovery card offers `[r] retry · [m] choose model · [×] dismiss` and adds nothing to the footer, because it names all three of its own answers.
  3. **A chip is a key.** `click()` does not answer anything: it records the key the chip names (`clickedKey`) and the input loop **falls through into the same branches a keypress reaches**. That is the whole reason a mouse answer cannot drift from a typed one, and it is why `m` still opens the picker with the failed turn set aside rather than a second "choose a model" path existing beside it.
  4. **`esc` is a `[×]` chip wherever it is offered, and every one of them is clickable**: the footer hints (`hintPairs`), a picker's title row, a menu's title row and its footer sentence (`hintLine` splits the caller's prose on the word), the clipboard menu's title and footer, and a card's own decision row. `closeChipHits` finds each chip by **walking the row it was drawn in** rather than by arithmetic in the caller, so a target can never drift from where the glyph landed, however the row was packed, padded or truncated. A chip the decision row's right edge would cut is neither drawn nor offered.
  5. **While a card is up, the card and the footer are the only click targets** — the page behind is scenery, and a row you cannot see clearly is not one you should be able to press (ADR-017). The footer stays in because its close chip is the permission card's way out.
  6. **Two bugs fixed on the way**, both found by writing the rows down. The recovery card's body was `split("\n").map(span)` with **no newline in front of each line**, and a row's spans are glued together — so a four-line gateway message printed as one run-on row, while the permission modal's `modalBody` had always prefixed `\n`. And the `[+]` attach hit box sat one cell left of the glyph: the hit test is compared against 1-based columns, and the box was computed as if they were 0-based.
- **Outcome**: 961 tests pass across 49 suites (two consecutive green runs), typecheck clean, ESM build 461.38 KB. New coverage: the card reports one target per chip with the columns it drew them in and nothing else while it owns the screen; a click on `[m]` opens the model picker and the picker's footer chip closes it; the card's `[×] dismiss` lets the error go while the error stays in the transcript; a permission prompt is answered by clicking `[a] always` and denied by the footer's `[×] deny`; and a multi-line gateway message gets one row per line. The old "never answers a permission prompt, wherever it is clicked" became "…when the click is not on a chip", because the card now does answer — deliberately — when a chip is what was clicked. Still keyboard-only, and deliberately so: `ctrl+c` (quit means quit), and the question panel's `tab` between questions — clicking an option answers it, but the tab strip is not a target yet.

## ADR-020: The Prompt Wraps, and the Box Grows With It
- **Context**: The owner typed one long line and sent a screenshot of the input box: the text ran to the right edge and stopped in a `…`. *"texts needs to wrap as it not showing one hit the window space."* The editor had always been one row — `editorView` returned one span run, and `paint` cut anything wider than the terminal with an ellipsis — so a long prompt, a pasted path or a wall of one character was silently unreadable, and the characters past the edge could not be seen, checked or edited. In a terminal the transcript has wrapped since ADR-011; only the box that is typed into did not.
- **Decision**:
  1. **`editorRows` replaces `editorView` as what the box draws**: the text is cut into rows that each fit the width, breaking at the last space that fits and mid-word when there is not one (`breakRows`) — a path or a run of one letter is still readable rather than clipped. The rows are code-unit ranges, so a row can report exactly which slice of the prompt it carries.
  2. **The box grows with the text, up to `EDITOR_MAX_ROWS` (6) rows and no further.** Past that the rows follow the caret, the way a multi-line input does: what is being typed is what has to stay visible, and a box that kept growing would eat the transcript it stands on. The rows under the first keep the first row's text column (badges included) so a wrapped prompt is one block of text, and the `[+]` control rides only the row being typed on — a `[+]` beside every wrapped row would read as one button per line.
  3. **The caret is measured against the row it wrapped onto**: `caretRow` is the last row starting at or before the cursor, so a caret sitting exactly on a break is drawn under it at column 0 rather than hanging past the row above. The editor's own selection is drawn per row, so a drag across a break shows on both.
  4. **The renderer reports the box's geometry** (`RenderedFrame.prompt: PromptBox`): the bar rows, the column the text starts in (`textLeft`, 1-based, badges included) and, per text row, the screen row and code-unit range it shows. A mouse cannot work this out for itself — the same row maps to a different offset once the text wraps — so a click that places the caret now asks the thing that knows where the breaks landed. This also deleted a guess: `app.ts` used to compute the text's left column as `attached.length * 10`, which was roughly right for image badges and wrong for document badges.
  5. **The chrome boundary is the box's top row**, not `caretRow - 2`: the caret moves as the prompt wraps, so the row where the transcript ends and the chrome begins moved with it, and a drag could otherwise start on the box's own upper row.
  6. **The caret column was one cell short** — `margin + 2 + caretCol` while the text starts at `margin + 3`, so the terminal's cursor sat on the space before the first character. Found by writing the wrapped rows down; visible in the empty box too, where the caret sat one cell left of the placeholder.
- **Outcome**: 975 tests pass across 49 suites, typecheck clean, ESM build 464.98 KB. New coverage: seven `editorRows` tests (a 200-character line arrives whole across three rows, a break prefers a space, a caret on a break lands on the row below, the window follows the caret past six rows, a wide character is never split, a selection crossing a break shows on both rows, the placeholder stays one row); five frame tests (the box grows instead of printing `…`, every row of the taller box carries the typing surface, the caret is the cell the next character goes in on the row it wrapped onto, the window moves to the tail past six rows, and the taller box takes its room from the transcript rather than the frame); and two live tests driving the real TUI — a click on the second row of a wrapped prompt puts the typed character there rather than at the start of the prompt, and a drag from that row to the end of the third copies the 79 characters between them. Test-maintenance note: `finish()` presses ctrl+u to clear the line, which only clears back to the caret — a test that leaves the caret mid-prompt now sends ctrl+a first, and both new tests were checked against the naive offset (they fail without `line.start`).

## ADR-021: The Input Box Is Fill Only, on a Lighter Surface
- **Context**: The owner sent a picture of the box with one line: *"make the input box are like this"* — a slate fill, no bar down its left edge, the mode row sitting on the same fill with nothing in front of it, and noticeably more air around the text — and, asked which parts to match, chose the lighter fill, the extra air and the missing bar, adding *"background colour will be follow as the theme colour"*. The box had worn a `▌` accent bar since ADR-004, and since ADR-018 it was filled with `theme.block` — the surface a user's turn wears — which on a near-black page left the typing area barely a shade off the transcript it sat on.
- **Decision**:
  1. **A new theme slot, `input`**, is the fill behind the box and its state row, and every theme answers it in its own palette: the dark themes step *up* from `block` (kicode `#1d1e2e` → `#2b2f47`), the light ones step *down* (`#eef2f8` → `#e2e8f2`), because on a light page a surface that is meant to sit in front reads darker, not lighter. The value is a slot and not a constant, which is what "follow the theme colour" asks for: switching to `nord` or `gruvbox` switches the box with it. `block` stays the user turn's fill, so the transcript keeps the weight it had.
  2. **The bar is gone.** The box's rows carry two cells of gutter as their padding — the same text column a request block's text has — and the state row loses its bar too, because it belongs to the box and the fill already says so. What marks the box out is the fill itself; the bar was doing that job while talking over the surface it was marking. The mode word keeps its own colour, which is where build/plan is read from.
  3. **More air**: two rows of the box's fill above the text and two below, where there was one of each. The text is not pinned to the top edge, and the gap between what is being typed and the state row that says where it will go is two rows rather than one. The box is therefore a row taller on every screen and the caret sits at row 20 of 24 instead of 21 — the transcript gives up that row, which is the honest price of a roomier typing area.
  4. **Nothing else had to move.** The bar's cell and its space became two spaces, so the text still starts in the same column (`textLeft` = the gutter + 3) — the caret column, the badge columns and every click that places the caret are unchanged arithmetic. The box lost a glyph, not a coordinate.
- **Outcome**: 975 tests pass across 49 suites, typecheck clean, ESM build 465.12 KB. The layout tests were re-pinned rather than rewritten: the caret-row test now says 24 − 4 and explains the two rows of air, the drag-highlight test moved its row to 20, "sits above the prompt box" locates the rule and asserts the five fill rows under it (and that none of them starts with a bar), the mode-row test drops the `▌` from its expected string, "one surface" now asserts `theme.input` and that no row of the box carries a bar, and the air test counts two blank rows instead of one. The transcript-column test still pins that the box's text lines up with a request block's text — the alignment outlived the bar. One test had to change size rather than numbers: "leaves a blank row between entries" counted blank rows, and the box being a row taller pushed that conversation into a scrollbar, whose thumb takes the last column of the rows being counted — it now draws a 30-row screen, where the four entries fit.

## ADR-022: A Card Is a Filled Surface, and Its Headings Have Their Own Hue
- **Context**: The owner sent a picture of the sessions list — wide, borderless, group headings in magenta, the row under the cursor filled edge to edge with a dot beside it, and a footer reading `delete ctrl+d   rename ctrl+r` with `current directory ctrl+a` pinned to the far right — and asked for it: *"make the sessions modal like this, and check how its fade the background when modal opens. like this sessios modal /models /connect /skill should appear."* The picker was a **framed** panel: `┌─┐ │ └─┘` in `theme.faint` around rows on the page background, capped at 68 columns, with group headings in the same faint grey as everything else and a `▌` cursor beside the selected row — while the settings/connect band (ADR-017) was already a filled surface with no frame. Two cards, two materials.
- **Decision**:
  1. **The picker is a filled surface with no frame.** Rows are `[page-coloured side padding, two cells of air, the content padded to the card's width, two cells of air]`, so the fill is a rectangle that starts and ends where the card does — the leading pad is painted on the page background, which is why the card does not run to the terminal's edge. The menu band's blank rows became spans of its own fill for the same reason: a surface with a gap in it is two surfaces.
  2. **It is as wide as the screen allows** (`PANEL_MAX` 68 → 84, `width = usable − 2·margin − 4`): a list of sessions or models is read down the screen, and a card that leaves a third of it empty is a card nobody asked for. The tab-context-menu pickers keep their narrow width — they are anchored under the tab they belong to.
  3. **Group headings get a hue of their own** — a new `heading` slot in every theme (magenta in the kicode palette, and each palette's own pink/purple elsewhere: `#d33682` in solarized, `#ff79c6` in dracula, `#b48ead` in nord, `#f5c2e7` in catppuccin). A heading names the rows under it rather than being one of them, and the accent is claimed: it is the colour of the row the keys act on.
  4. **The row under the cursor is filled, and that is the whole mark.** The `▌` cursor is gone from the list rows — a fill and a bar beside it say the same thing twice — and the row's own text switches to the fill's foreground (`styles.paletteSelected`), so a selected row is one object rather than white text on a coloured band. The dot for the session in use stays, which is what the reference shows the dot for.
  5. **A card's own footer has two ends.** The hint pairs run from the left except the last, which is pinned to the card's right edge when there is room for it — a footer with a beginning and an end instead of one run of keys that happens to stop early.
  6. **The sessions card names a key it did not have**: `ctrl+d delete`, wired through the same `extras` machinery the model list uses for `ctrl+f`, so the key acts on the row under the cursor, the card stays up, and the list is rebuilt from what is left. The reference's `ctrl+r rename` and `ctrl+a current directory` are **not** built: renaming another session has no store path (a title is written with the session that owns it, and `/rename` names the one in front), and the listing is per-directory by design. A card must not print a key that does nothing.
  7. **The fade is unchanged, and was checked.** A picker or a menu still renders the conversation behind itself and drops every page row it does not cover to the faint style on the page background (ADR-017), while the tab bar, the state row and the footer keep their colour. What changed is that the card is now *opaque* where a blank row would previously have let the page through, which is what makes it read as a surface rather than as a list drawn on the transcript.
- **Outcome**: 978 tests pass across 49 suites, typecheck clean, ESM build 466.74 KB. New coverage: a group heading carries `styles.heading` and not the accent; a card's last key ends at the card's own inner edge (two cells past the title's close box, which carries its own trailing air); the row under the cursor carries the accent fill and the card contains no cursor glyph at all; the card is one panel fill with no border glyphs and starts inside the terminal's edge; the card's last row is the page's last row, one row above the rule. In the live TUI: `/sessions` names `ctrl+d delete`, and ctrl+d deletes the row under the cursor — the second row, not the first — leaving the card up with the remaining rows. Tests that pinned the frame were re-pointed at the fill: `▌  m2` in the favourites test became a fill-coloured `m2` read off the painted frame, and the faded-page test now looks for the fill rather than the accent on the selected row.

## ADR-023: The Mode Is a Button on the Box's Left Edge, and Upload Is Spelled Out
- **Context**: The owner sent a picture of an input box — `Ask anything...` in a rounded frame with a `PLAN` pill at its right edge, and a state row under it reading `Plan · muse-spark-1-3-contributor:free · default` — with one line: *"i want chat area exact same like this, just put the plan in the left side and small upload button on the right side."* Asked what the pieces should be, they chose: the pill **cycles the mode on click**, the state row **drops the mode word** (it would be the same answer twice), and the right-hand button reads **`UPLOAD[+]`**. The mode had been keyboard-only since it was added (`Shift+Tab`, `/mode`) and drawn as the first word of the state row since ADR-004; the right-hand control has been `[+]` since ADR-016.
- **Decision**:
  1. **The mode is a pill on the box's left edge, and it is a button.** `[BUILD]` / `[PLAN]` / `[PAUSED]` / `[GOAL]` — the word in brackets, the shape `[esc]` and `[y]` already have — with the word in the mode's own colour (`styles.mode`, or `styles.warn` when the mode is not the everyday one, which is the rule that has always said "this session has stopped writing files") and the brackets in `styles.pillBorder`, a theme slot that existed and nothing had used. A click runs the same `toggleMode()` that `shift+tab` runs. It leads the row rather than trailing it because it answers the question the row is about: what this box will do with what is typed into it.
  2. **The right-hand control is `UPLOAD[+]`** — dim word, glyph in `styles.plusButton` (also a slot the theme already had): the word because a bare `[+]` is a riddle, the accent on the glyph because the glyph is the part that is pressed. "Small" was the ask; a button whose meaning has to be guessed is not small, it is short. Its job is unchanged: the platform's own file-selection window.
  3. **The mode is named exactly once on screen.** With the box up the pill says it, so the state row drops its leading word and reads `model · variant`; with a card up (a picker, a menu, a permission prompt, a question that is not being typed into) there is no box, so the state row leads with the mode as it always did. The rule is about the mode specifically: the busy row, a notice and the copied line are what the session is *doing*, and they keep the row they had. `modeWord()` is now the single place the words and their colours live, so the pill and the state row cannot disagree about which mode the session is in.
  4. **Both buttons' columns come from the renderer.** `PromptBox` gained `modeButton` and `uploadButton` — a screen row and a column range each — and `app.ts` presses those rectangles rather than re-deriving the geometry. The pill's width *is* the mode's own word, so nothing outside `renderBottom` can know it; and the `UPLOAD[+]` hit box had been arithmetic in a second file since ADR-016 (which ADR-019 had already had to correct by a cell). This removes the class of bug rather than the instance. The same reasoning applies to a wrapped row's lower lines: the app presses only the rectangles it was given, and the renderer reports one row for both buttons.
  5. **The caret column is asked for, not assumed.** `renderFrame` computed it as `margin + 3 + caretCol`; it is now `bottom.prompt.textLeft + caretCol`. The gutter, the pill and the badges all sit in front of the text, a glyph on the left shifts every column after it, and the box is the only thing that knows how wide that glyph is.
  6. **The text column moved, and the wrapped rows kept theirs.** The pill and its gap take ten cells of the row's budget, so a long prompt breaks sooner — a 200-character line is four rows where it was three — and the rows under the first pad the pill out rather than drawing it again: one pill per wrapped line would read as a column of buttons, and `UPLOAD[+]` stays on the row being typed on for the same reason.
  7. **One behaviour retired.** A click on the empty left side of the box used to open the clipboard-and-attachment menu; that cell is the pill now. The menu is still on the prompt's right-click, which is where the transcript's own menu is, and no test covered the left-click path (it was never named anywhere a user could read).
  8. **The README was brought back in step.** Its interface sketch still drew the box with `▌` bars and its prose still said the mode was "the first word on the state row" — a decision ADR-021 had already reversed and this one finishes. A picture of the UI in the documentation is a claim about the UI.
- **Outcome**: 982 tests pass across 49 suites (two consecutive green runs), typecheck clean, ESM build 467.92 KB. New coverage: the renderer reports the cells it drew each button in and which row they ride, and neither sits on the text; the pill cycles `build → plan → build` from a click on the real TUI, and the state row leads with the mode on a screen where the box is not drawn, so the "exactly once" rule is pinned from both sides. Tests re-pinned: the bottom-bar test reads `gpt-5.6-luna · high` off the state row and looks for the pill on the row above it; the mode tests moved to the pill (`[BUILD]`/`[PLAN]`, plan still carrying `styles.warn`) and the mode/model pairing became "the pill and the prompt share a row"; the "one surface" and "row of air" tests find the state row by the *last* row that names the model, because the transcript's own header names it too; the box test that counted the wrapped rows of a 200-character line says four; the transcript-column test now pins the box's own left edge — the pill — at the request block's text column, with the words one gap behind it; and the wrapped-prompt click tests find their rows by the run of typed text, since the first of them opens with the pill.

## ADR-024: Compaction Aims at a Size, Not at a Count of Turns
- **Context**: The owner's sixth issue, in their own words: *"**Compact to 30–50% while keeping task context** — compaction currently cuts too little/too much; target 30–50% of the window with all task-relevant context preserved."* The cut was `splitIndex(messages, keepRecentTurns)` — the Nth-newest **user** message, six by default — and that one line was the source of both halves of the complaint. Too little: the kept turns were never measured, so a session kept at the trigger could come back at the same size or bigger and be compacted again on the very next turn, paying a model call each time to make no progress; worse, a session with fewer turns than the knob held at all (`userIndices.length <= keepRecentTurns → null`), so a long autonomous run with one enormous turn could never be compacted at all and simply grew until the window broke it. Too much: six turns can be a few thousand tokens, so a 100K session could be summarised down to 10K — most of the conversation replaced by prose that did not need to replace it, and the session left with room it had no reason to spend.
- **Decision**:
  1. **The target is a size, and it is stated in the open.** `compaction.targetPercent` (default 40, clamped to the 30–50 band by `clampTargetPercent`) is where a compacted session sits in its window, and `compactionTarget()` turns it into tokens — never more than the window the reserve leaves, because a target larger than the usable window would be aiming at room that does not exist. The band is the point: below it the session has been summarised past being useful, above it there is no room left to work in, which is what compaction is for.
  2. **The tail is the longest run of recent turns that fits the target.** `planCompaction` walks the cut forward from the oldest candidate and takes the first whose tail already fits; if none fits it takes the smallest legal tail. So the session lands *at* the target rather than wherever a count left it, and the sum of the tail and the briefing is what the notice reports. A session already at or under the target has nothing to gain, so `planCompaction` returns null and no model call is spent — which is also what makes `/compact` honest: it says it has nothing to do rather than compacting a session that fits.
  3. **The briefing is given a budget too.** The summary is asked to stay under a fifth of the target, said out loud in the instructions (`summaryPrompt(budget)`), and that fifth is reserved out of the tail's budget before the cut is chosen — a summary that runs long is precisely what pushed sessions back over their target after compacting. The model is prose, not arithmetic, and it may overshoot; the ceiling is what the cut is planned against regardless.
  4. **A cut prefers a request, and may fall back to the middle of a turn.** Requests first: a tail that opens on the words that prompted the work reads as a conversation, every kept turn carries its own question, and it is the boundary providers are happiest with. Only when no request cut fits — one enormous turn, a hundred tool calls under a single question — does the cut move inside the turn, to an `assistant` message that owns its own calls. That fallback is the whole fix for the case that used to do nothing at all.
  5. **Which boundary moves the cut is a function, not a comment.** A `tool` message may never open a tail (it needs the call before it), and a repaired cut only ever lands older than the message it was asked about. `pairedCut` walks the kept slice looking for a tool result whose call is not in it — the same check the test helper has always made — and moves the cut back to the call's own message. For a well-formed transcript it never fires; it is there because the pairing is a hard API error and "the cut cannot land there" is worth more as code than as a promise.
  6. **Suffix sizes are computed once.** A plan weighs a cut at every message against the budget, and `estimateTokens(messages.slice(cut))` per candidate would stringify the transcript once per message. `suffixSizes` computes every suffix's cost in one pass — the same four-characters-per-token estimate, one JSON length per message, exactly the string the array would serialise to — so the plan is linear in the transcript rather than quadratic.
  7. **`keepRecentTurns` is gone.** It is a turn count, a turn is not a size, and the count *was* the bug. A config that still sets it is told so and ignored (`"Ignoring \"compaction.keepRecentTurns\" … use \"compaction.targetPercent\""`) rather than dropped in silence: a knob that does nothing is worse than one that says it does nothing. `KICODE_KEEP_TURNS` goes with it, replaced by `KICODE_COMPACT_TARGET`.
  8. **Both notices and the transcript line say what was aimed at**: `compacted 12 earlier messages · ~100.0K → ~43.0K tokens (target ~51.2K)` — *how far it fell* was the only number the old line gave, and the aim is the thing a user can now check.
- **Outcome**: 993 tests pass across 49 suites (two consecutive green runs), typecheck clean, ESM build 471.54 KB. Verified against realistic shapes with a scratch harness (since deleted): a 107K-token session of thirty turns compacts at its trigger to a tail of ~39.2K — 30.6% of a 128K window, 30.6–38.6% once the briefing's own room is counted — keeping 44 of 121 messages where a count of six kept six; a 104K session shaped as *one* enormous turn, which the old rule refused to compact at all, now cuts inside the turn (78 of 202 messages, every tool pair intact) and lands at 31.8–39.8%; and a 12K session reports nothing to gain. New coverage: the target is a share of the window, is clamped into the band whatever it is asked for, and never exceeds the window the reserve leaves; the tail is the longest that fits and one turn further back does not; a cut prefers a request over an older cut inside a turn (pinned by a ladder of equal-sized messages); a cut moves inside a turn when one enormous turn is all there is; a cut is moved back rather than orphan a tool result; and the briefing is asked for a fifth of the target. Re-pinned: the four `shouldCompact` option objects, the whole `splitIndex` describe (replaced by `planCompaction`), the two `compactMessages` transcript tests (they were small enough that the planner now correctly says there is nothing to gain — a compaction test has to be over its target), `config.test.ts`'s defaults and environment read, `init.test.ts`'s five compaction fixtures, `settings-file.test.ts`'s merge test (plus the new warning test), and the loop's live compaction test, which now talks in ~500-token turns until it compacts and asserts the turn it happened in — `question N` — survived word-for-word while everything before it became a briefing. The TUI's own compaction shows the target on its transcript note, which is pinned.

## ADR-025: A Turn Ends at an Answer, Not at the Absence of a Tool Call
- **Context**: The owner's eighth issue, in their own words: *"**Agent sometimes stops mid-task** — a turn ends before the work is done; find the stop and make it continue reliably."* There were three stops, and only the last one was a number. The loop's rule was `calls.length === 0 → done`, and it never looked at *why* the endpoint stopped writing. So (1) a reply the endpoint's own output cap cut off — `finish_reason: "length"`, which KiCode never asks for a `max_tokens` and therefore never sees coming: the gateway's default is the cap, often 4 096 tokens — was filed as an answer, and the turn ended mid-sentence with the work half done; (2) a reply with neither words nor a tool call (`content: null`, no calls) was also an answer, so the turn ended having done nothing at all, which is the purest form of "it just stopped"; and (3) the request budget was 12, which ordinary work reaches — look, read, edit, verify across a few files is 12 requests before anything has gone wrong — and running out of it ended the turn with no line anywhere saying so. `DEFAULT_MAX_TURNS` was also written down twice, in `loop.ts` and `config.ts`.
- **Decision**:
  1. **`done("complete")` is reached only on an answer.** An answer is a turn that asked for tools, or one that said something and was allowed to finish (`finishReason === "stop"`). A reply cut off by the endpoint, and a reply with nothing in it, are neither — the model did not finish and did not say it had — so the turn asks again instead of ending. This is the fix the owner asked for: the stop was the loop's rule, not the model's, and the rule was wrong.
  2. **A cut-off reply is kept and built on.** The words the model had already written are pushed into the transcript exactly as they arrived, so the next request continues the half-finished thought rather than starting the answer again — the same reasoning `keepPartial` has always used for a cancelled turn. A reply with *no* words is deliberately not kept: an empty assistant message is a turn the model never really made, some endpoints refuse one back, and re-asking the identical question is the honest move.
  3. **The asking is bounded.** `MAX_CONTINUATIONS = 3` replies in a row may be re-asked, and the allowance is given back by any turn that ran a tool — progress is the thing the bound exists to protect. Without it an endpoint that always truncates would be asked forever, which is worse than the truncation it is working around. The refusals count against the ordinary request budget like any other request, so the loop's outer bound still applies.
  4. **The stop is said out loud** — a new `continued` event carrying which way it stopped (`truncated` / `empty`) and which attempt this was, rendered as a dim transcript note (`the reply was cut off — asking it to carry on`, `the model answered with nothing — asking again`) and a dim line in one-shot mode. The user watched the model stop mid-sentence; telling them the endpoint's cap did that, rather than the model, is the difference between a glitch and something they can act on.
  5. **The budget is bigger, and it speaks.** `DEFAULT_MAX_TURNS` is 40 — still a bound on a model that never stops, but no longer one a real task hits by accident (the owner chose this outright over continuing past the budget while tracked work remained, and over any continuation machinery on top). A turn that does reach it now pushes a warn note, `turn budget reached — send anything to carry on`, in the TUI and a dim line in one-shot mode; before this the transcript simply ended, which is precisely how "the agent stopped mid-task" reads from the outside.
  6. **The default has one home.** `DEFAULT_MAX_TURNS` is exported by `loop.ts` — the module that spends it — and `config.ts` imports and re-exports it, the way it already does `COMPACT_TARGET_PERCENT` from `compaction.ts`. Two copies of a number that must agree is a bug waiting for someone to change one of them.
- **Outcome**: 1001 tests pass across 49 suites, typecheck clean, ESM build 472.84 KB. New coverage: a reply cut off at the cap is continued, the truncated words are what the next request is built on, and the turn still ends `complete` when the model eventually finishes; a reply with nothing in it is re-asked with an *identical* request (`requests[1].messages` equals `requests[0].messages` — nothing was added for the model to read) and no empty assistant message is recorded; an endpoint that never finishes a reply is asked exactly three extra times and not a fourth; the allowance is restored by a tool call between two truncations (two continuations, both `attempt: 1`); a continuation counts against the turn budget like any other request; and the transcript renders both notes plus the budget warning under a `max-turns` end. Pinned: `loadConfig` gives 40. Re-pinned incidentally: nothing — the existing `maxTurns: 3` loop test and the budget `done` tests already described the behaviour this preserves.

## ADR-026: Clipboard Image Preview & Last-5 Persistent History
- **Context**: The clipboard context menu lacked visual inspection for images before pasting/attaching, and only reflected whatever was currently on the system clipboard without history. Users needed to inspect images before attaching and easily recall/paste from recent clipboard items.
- **Decision**:
  1. **True-Color Thumbnail Rendering**: Built `decodeImagePreview` in `clipboard.ts` using Node.js built-ins (`node:zlib`). It decompresses PNG scanlines and downsamples to a 24×6 thumbnail rendered with ANSI true-color half-blocks (`▀`). Colors are encoded in `span.style` so they survive `sanitiseText` and `truncateSpans` without color stripping.
  2. **Last-5 History Persistence**: Added `ClipboardHistoryItem` tracking with JSON persistence at `~/.kicode/clipboard_history.json`. Up to 5 text and image entries are automatically saved across session copies (`writeSelection`, `copyTranscript`) and clipboard context menu opens.
  3. **Interactive Menu & Dynamic Preview**: The clipboard modal displays history items with quick 1–5 key selection and full-row mouse hit targets. Navigating entries via `↑`/`↓`, mouse hover, or mouse wheel dynamically updates the modal preview card to show the focused item's thumbnail or text snippet.

## ADR-028: The Turn Continues While Tracked Work Remains, and the Queue Is a Place You Can See
- **Context**: The owner raised three things in one pass. *"The agent must understand where to ask a question, and when to continue. As of now sometimes it's getting stopped."* — the second half of the issue ADR-025 fixed: that fix made a *reply* count as an answer only when it was allowed to finish, but a reply that genuinely stops with the `todo` or `goal` tool still holding open work was still accepted as the end of the turn, and the system prompt gave the model no rule about when asking was warranted. *"When sending another message while a turn runs, it waits"* — the queue existed (`/queue`, `/insert`) but was invisible: you could not see what was queued, and could not drop one entry without clearing the lot. And *"If user picks `/goal` or `/insert` from the options list … it must execute automatically"* — choosing `/goal` from the palette submitted bare, printing a usage line, while `/insert <msg>` typed at an idle prompt sat in a queue that no turn would ever drain because nothing was running.
- **Decision**:
  1. **The loop asks a tool, not a special case.** `Tool` gained an optional `pendingWork(): string | null`, implemented by the `todo` tool (open checklist entries) and the `goal` tool (a running goal's unfinished subtasks). Before accepting `done("complete")`, `loop.ts` walks the registry through a small `pendingWork(tools)` helper; a registry with no such tool answers null, so the cost to every other tool is nothing. A tool that knows what it is holding says so, and the loop only asks — the alternative (the loop reading the plan state directly) would have coupled the turn loop to two concrete tools.
  2. **The nudge is bounded, and progress pays it back.** At most `MAX_CONTINUATIONS` (three) in a row, exactly like the truncated/empty re-ask, and any turn that ran a tool resets the allowance — progress is what the bound exists to protect, and a model that refuses the work must not be asked forever. The nudge is itself a user-role message naming what is outstanding, and it tells the model the three honest ways out: continue the work, mark the remaining steps done or clear the list and say what changed, or use the `ask` tool if it is blocked on a decision only the user can make.
  3. **Plan mode is exempt.** An open list in plan mode is the plan, and the deliverable there is stopping for review — the guard is skipped when `readOnly` is set.
  4. **The prompt draws the line, because the guard only catches tracked work.** `DEFAULT_SYSTEM_PROMPT` now says to work to the end of the task in one turn (don't stop to report progress or ask whether to continue) and to reach for `ask` only when the decision is genuinely the user's — a preference, a trade-off, a name, how far a destructive change should reach — choosing a reasonable default, saying in one sentence what was assumed, and continuing otherwise. The enforcement is the guard; the prompt is what keeps the guard from having to fire on every task.
  5. **A third `continued` reason, `work`**, so the stop is announced the way the other two are: `tracked work is not finished — asking it to carry on`, in the TUI transcript and in one-shot output.
  6. **The queue is drawn above the box.** Each queued message is a titled tile with its own `[x]`, and the renderer reports the chip's screen row and columns under a new `PanelKind: "queued"` carrying the queue index — so a press can only ever drop the message it was aimed at. A tile list that updates is the feedback; a notice cannot be shown while the spinner owns the state row, which is exactly when the tiles are visible.
  7. **`ADD[+]` queues what is typed**, in the `UPLOAD[+]` idiom, and is shown only when there is a turn (or a paused session) to queue behind. Idle, enter already sends, and a button that is always there takes width from every prompt to say something the keyboard already does.
  8. **A drained line that starts with `/` runs as a command.** `runQueued` dispatches to `command()` when the prompt is a slash command and to `runTurn()` otherwise, and every drain site (the turn's `finally`, `/resume`, the paused-submit path, `releaseHeldQueue`) goes through it. A `/goal …` typed mid-turn used to be handed to the model as prose — the queue and the transcript were the only things that agreed it was a command.
  9. **A command that needs an argument fills the box instead of running.** `usage` written in angle brackets means required (square brackets mean optional); choosing such a command from the palette, or typing it bare, puts `/cmd ` in the box with the cursor waiting. The palette's Enter handler and `command()` both consult the same rule, so a pick and a typed command cannot behave differently. `/insert <msg>` and `/queue <msg>` run at once when idle, because with nothing in flight there is nothing to insert ahead of — a queue no turn will drain is not a queue, it is a message that got lost.
- **Outcome**: 1017 tests pass across 49 suites, typecheck clean, ESM build 498.09 KB. New coverage: the loop nudges a turn that answers with a `pendingWork` tool still open and ends `complete` once it is cleared; a model that never clears the list is nudged exactly three times and not a fourth; plan mode is not nudged at all; the transcript renders the `work` reason. In the renderer: the `ADD[+]` button appears only while busy, and its reported columns land on the label; each queued tile's `[x]` hit covers exactly the glyph. Driving the real TUI: choosing `/go` fills `/goal ` without sending and runs on the argument; an idle `/insert <msg>` sends at once rather than queueing; a `/goal` typed mid-turn runs as a goal when its turn arrives; `ADD[+]` queues the box's text and clears it; and clicking a tile's `[x]` drops that one message, leaving the rest of the queue in order. Re-pinned: none — the idle layout is byte-identical, which is why the button is conditional rather than permanent (the attach tests and the wrapped-prompt test caught the width change immediately).
- **Also in this pass**: the tracked `.env.example` template was found to contain three real API keys; the values were blanked and a warning added, and the keys must be rotated because they are in git history.

## ADR-029: The Plan Panel Reads State, Not Text
- **Context**: The owner asked for *"a todo button in the below chatbox"* that opens *"a modal with the details todo, with progress"*, on the *"right side above the chatbox"*. The obstacle was not the drawing: the live checklist only exists inside the `createPlanTools()` closure, and the only thing that ever left it was the **rendered text** of `renderTodos` / `renderGoalCard` in a transcript `result` entry. A progress bar read off a text tree would be a parser held together by whatever glyph the last renderer happened to use. The owner also reported opencode.ai free models failing with a 403 again.
- **Decision**:
  1. **A tool can hand its state over as data.** `Tool` gained an optional `snapshot(): PlanSnapshot | null`, implemented by both plan tools (they share one session state, so either returns the whole thing — a goal call is as good a moment as any to refresh the checklist beside it). The types live in `tools/types.ts` so the loop and the renderer can name them without importing the tools.
  2. **The loop forwards it as a `plan` event.** Emitted right after the `tool-result`, so a screen sees the same update the model does, in order. A tool with no state emits nothing, and every other tool pays nothing.
  3. **The app holds the snapshot, not the agent.** It is the screen's copy: it survives an agent rebuild (a model switch) and is what the last turn left behind, which is exactly what a button should keep showing.
  4. **The chip is a button on the state row, and only exists when there is work.** `[TODO n/m]`, right-aligned on the row that already carries the session's own status. A running goal's subtask progress is preferred in the label — the goal is the headline, the checklist beside it is a means to it. Nothing tracked, no chip: `TODO [0/0]` on a quiet session is a button for nothing. It is also withheld while a card (a permission prompt, a failed turn) owns the screen, because the panel it opens is hidden then and a button that visibly does nothing is worse than one that is not there.
  5. **The panel is narrow, right-aligned, above the box.** A glance, not the transcript: checklist rows with `✓`/`◐`/`○`, a ten-cell bar, and — when a goal is running — its status, title, subtasks and current task. It is hidden with the box, so a card that owns the screen is not sharing it. `esc` closes it first among everything closable, and its `[×]` is a click target found by walking the title row it was drawn in (the same `closeChipHits` guarantee every other `[×]` has).
  6. **The renderer reports the chip's columns** as a `todo_button` hit, like the queue tiles' `[x]` — the app presses what it was given rather than re-deriving the pill/state-row arithmetic.
  7. **A bare 403 on opencode.ai is the client gate.** Credentials are a 401; a 403 means the request was understood and refused, which on that endpoint is the client restriction. The note used to wait for the body to carry an OpenCode-shaped `AuthError`, which the newer responses do not send — so the user got "rejected the API key" for a key that was fine. A 401 still requires the body to confirm it, because a 401 genuinely can be a wrong key. `--probe` matches on the same sentence, so it inherits the diagnosis. **This does not make client-restricted free models work** — that gate is server-side; it makes the failure say so and name the ways round it.
- **Outcome**: 1024 tests pass across 49 suites, typecheck clean, ESM build 504.48 KB. New coverage: a tool with a `snapshot` emits a `plan` event carrying it and a tool without emits none; the chip shows the checklist's progress and reports the columns it was drawn in, prefers a running goal's subtask count, and is absent when nothing is tracked; the panel is absent when shut, draws the checklist and the goal when open, is right-aligned inside the terminal's edge, and its `[×]` is a target on the title row; and, driving the real TUI, the chip opens the panel and Escape closes it. For the 403: a bare `403` with no `AuthError` body now names the client restriction, while a 401 on another gateway still does not.

## ADR-030: The Brain Is Read Back, and the Agent Knows When to Write
- **Context**: The owner asked for the agent to be "more intelligent … know when to remember and store data". Auditing it found the writing was never the whole problem. `remember` (ADR-008) saved a skill or a project memory with real guardrails, and the system prompt had exactly one line about when to use it — *"when you verify something reusable … save it"*. But **nothing read the brain back**: the directory's `AGENTS.md` was folded into the system prompt, while skills and memories reached the model only if a human or the model typed `@project:…` or `@skill:…` by hand. A brain that is only written is not memory, it is a journal nobody opens, and the vaguer the write rule, the more the journal fills with trivia: one-off command output, code restated, the same fact appended again every session.
- **Decision**:
  1. **Brief the model at session start.** `brainBriefing()` reads the brain and returns a bounded block — this project's memory text (capped), then skills by **name and description only**. It is folded into the system prompt exactly where `AGENTS.md` is read, in `instructionsFor()`, so it is there before the first request and needs no promise in the path (the writer that reads it is synchronous, like the `AGENTS.md` read already was).
  2. **Bodies are not in the briefing, on purpose.** A skill body is a page; every body in every request is how a brain becomes a cost instead of an advantage. The briefing names things; the model asks for the ones that matter.
  3. **A `recall` tool is the other half.** `recall` loads a skill or memory by exact `name`, or searches by `query` over skill names and descriptions, then project slugs, then the contents of a bounded number of memory files. A miss answers with an inventory of what does exist, so the model's next call can be right instead of a guess. It is ungated and works in plan mode: reading changes nothing, and a prompt for it would cost more than the read.
  4. **The write rule became a policy.** The single line is replaced by three: read the brain before planning (load a body when a name looks relevant); save when the session produced something durable — a stated preference or decision, a non-obvious gotcha with its fix, a project convention the code does not show, a procedure of three or more steps worth repeating — and add to this project's memory rather than repeating it; and do not save one-off output, restated code, speculation, transient errors, or anything already recorded, and never a secret.
  5. **A skill can be corrected.** `remember` gained `action: "update"`, which replaces an existing skill's body. A plain save still refuses to overwrite — replacing a skill has to be deliberate — and an update of something that does not exist says so rather than quietly creating it.
  6. **The reader walks the tree.** `remember` writes one level (`skills/<name>/SKILL.md`), but a maintained brain categorises them (`skills/android/adb-automation/SKILL.md`). The first cut of the sync reader looked one level down and found roughly a tenth of the real library; it now walks breadth-first, bounded by directories visited as well as skills found.
- **Also fixed, found by this work**:
  7. **The compaction planner ignored the system prompt.** `planCompaction` measured the tail against the target but never counted the messages the cut cannot touch — the system prompt — so a compacted session landed at *target plus the prompt*, an overshoot that grows with the prompt. The prompt's own size (and any pre-existing briefing above the cut) is now spent out of the target before the tail is chosen, which is what makes ADR-024's "lands at the target" true for any prompt.
  8. **Quoted frontmatter was read with its quotes.** `remember` writes `description: "…"`; both readers (the new one and the mention index) returned the quotes as part of the description, so a skill's one-line summary displayed them. Both strip matching surrounding quotes now.
- **Outcome**: 1036 tests pass across 50 suites, typecheck clean, ESM build 514.36 KB. New coverage: a directory's memory slug comes from its own name; the reader finds the skills and memories the writer made; the briefing carries this project's memory text and the skill names/descriptions but **not** a body; a directory with no memory of its own is told which projects do exist; no brain means no briefing; `recall` loads a skill and a memory by name, finds a skill from words in its description, answers for the current project when asked for nothing, and on a miss lists what does exist rather than guessing; nested skills are found; both halves are registered and neither needs approval; and `remember` replaces a skill only on an explicit update, refusing otherwise and refusing an update of something that does not exist. Verified against the real workspace brain (`ki-agent-brain`, 146 skills across nested categories, plus project memories): the walk finds the categorised ones, and a project with no memory of its own gets the skills list and the names of the memories that do exist.

## ADR-031: A Fresh User's Brain Is Created, Not Demanded
- **Context**: The owner asked the question that the whole brain design had never answered: *"for a new user with no `ki-agent-brain`, how does it learn and build skills over time?"* Reading the code gave a blunt answer — it does not. A brain was found only two ways: `KI_BRAIN_PATH`, or a walk upward for a directory **literally named `ki-agent-brain`** (ADR-008). There was no config key and no default location, and although `remember` created the `skills/…` and `memories/…` subfolders, nothing ever created the brain itself. So a new user's first `remember` failed outright and nothing ever accumulated: the read-back work of ADR-030 made a brain *useful*, but only for an owner who already had one.
- **Decision**:
  1. **The default brain is `~/.kicode/brain`** — one per user, inside KiCode's own home (so it follows `KICODE_HOME`), with per-project memories kept inside it under `memories/projects/`. The owner chose global-over-per-repo explicitly: learning from one project should be available to the next.
  2. **Resolution is a four-step order**: `KI_BRAIN_PATH` → a `brain` path in `kicode.json` (global first, then the project file) → an existing `ki-agent-brain` at or above the working directory → `~/.kicode/brain`. Each later step is a fallback, never a competitor: an explicit path still wins, and the old upward walk is kept so an existing brain is never abandoned by the upgrade.
  3. **A save creates a brain; a read only reports one.** `readBrain`/`resolveBrainDirSync` still return null when there is nothing to read — that is honest. But `ensureBrainDir` (used by `remember`) creates the configured path, or `~/.kicode/brain`, on the first save. The `ki-agent-brain` walk is deliberately **not** a creation target: it is how you keep using a brain you have, not where a new one is scattered.
  4. **The `brain` config key is read synchronously.** The briefing is assembled before the first request, in the same place `AGENTS.md` is read, so there is no `await` on the path. `readConfigBrainSync` reads the same two files `readConfigFiles` does, for that one key only; a config that will not parse is already reported by the async reader and is simply a miss here. `~` expands to the home directory and a relative path resolves against the working directory.
  5. **No hosted "harness model".** The second half of the owner's question — learning automatically over time, the way Hermes-style agents do — is a *second LLM call* over the transcript that extracts durable skills and preferences, not a service. A hosted harness would break KiCode's governing rule (no account, no server); the extraction runs on the user's own BYOK key. This ADR ships only the bootstrap that makes such a pass possible; automatic extraction and a separate always-injected "taste" layer are their own, later decisions.
- **Outcome**: A fresh user's first `remember` succeeds and writes to `~/.kicode/brain`, and every later session reads it back through the existing briefing and `recall`. An existing `ki-agent-brain` (the owner's own, 146 skills) still resolves and still wins over the uncreated default. `kicode.json` gained a validated `brain` key, and `--help` names `KI_BRAIN_PATH` and the default. Verified: typecheck clean; 1043 tests across 50 suites (seven added — config path, `KI_BRAIN_PATH` precedence over config and walk, the walk itself, the default once it exists, creation of the default, creation of a configured-but-missing path, and validation of the `brain` key); ESM build 516.72 KB; `--version` 0.1.0.

## ADR-032: The Skill Registry Is a Distribution Channel, Not a Runtime
- **Context**: The owner is planning a website that lists skills so users can install the ones they need, with one hard condition — *"the intelligence must be available if anyone using KiCode"*. This is the "generic configurable skills repo" the roadmap parked as not built (`ROADMAP.md` §1, `TODO.md` line 98). The machinery it sits next to already exists: the brain (ADR-031), the prompt briefing and `recall` (ADR-030), `remember`, `/skills`, and `@skill:` expansion. The question is not how to list skills — it is how a registry can exist without turning KiCode into a product that needs an account, a server, and a network.
- **Decision**:
  1. **Two layers, never conflated.** *Intelligence* — the briefing, `remember`/`recall`, and the eventual auto-extraction pass — ships inside `dist/cli.js` and is on for everyone the moment KiCode is installed; there is nothing to fetch and no sign-in. *Skills* are optional content a user may add. The registry website is **discovery and distribution only**, like a package page: browsing, listing and installing are its whole job, and its absence changes nothing about whether KiCode learns.
  2. **The registry is never a runtime dependency.** KiCode does not fetch skills, check for updates, or call the site mid-session. A user with zero installed skills, offline, still gets the full learning loop; the marketplace adds breadth, not brains. Removing the website must be a no-op for the CLI — that is the test this decision has to keep passing.
  3. **One curated official repo is the source of truth.** Skills live at `skills/<category>/<name>/SKILL.md` in a repo the owner controls, reviewed by PR. No open submissions, no database, no accounts. This layout is deliberate: it is exactly what the brain already uses, and exactly what the `npx skills` CLI discovers (it walks `skills/<name>`, `skills/<category>/<name>`, and one deeper, shallow shadowing deep). Format is unchanged from `remember`: `name` + `description` frontmatter.
  4. **The manifest is generated, never hand-written.** A build step emits `skills.json` from the repo — `name`, `description`, `category`, `version`, `sha256`, `author`, `source` (path + commit). The website renders from it and nothing else, so the site cannot drift from what actually installs, and a changed skill body is detectable by hash rather than by trust.
  5. **Distribution is the existing `npx skills` CLI**, per the owner's choice. A skill installs with `npx skills add <owner>/kicode-skills --skill <name> -y`, or the whole set with `--all`. KiCode grows **no new install command** for this: writing a second package manager is how two package managers end up disagreeing. The website's button simply copies that line.
  6. **KiCode reads what the CLI writes.** This is the seam that needs code, and it has two halves. **Now:** KiCode gains a small, ordered list of *skill roots* and reads the `.agents/skills/` convention (project and user level) alongside the brain — so a skill installed with `-a universal` is found today. **Upstream:** a PR to `vercel-labs/skills` adding `kicode` to its agent table (project `.kicode/skills/`, global `~/.kicode/skills/`), so installs are first-class and land beside the brain. Until that lands, the docs name the universal target.
  7. **Learned and installed skills are kept in separate roots, on purpose.** A *learned* skill is this user's own session output (the brain); an *installed* skill is checked-out content from a registry. Separating them makes provenance legible, lets `skills update` or a removal touch only what was installed, and means a registry can never silently overwrite something the user's own sessions wrote.
  8. **Curated means reviewed, and a skill is still untrusted input.** The trust model is "one maintainer reviewed every entry", pinned to a git commit and a content hash — no community tier yet (the manifest keeps a `verified` field so a tier can be added later without changing the format). But a skill body is instructions the model will follow, which is closer to installing a *prompt* than a package, so three rules hold regardless of the tier: **install writes files and never executes anything**; KiCode never runs a skill body as a command, only ever as model context (already true — skill bodies are expanded as context by `@skill:` and loaded by `recall`); and the body is shown to the user before install (the `/skills <name>` card, and the website).
  9. **The website is static and generated.** Search and filter by category, each card showing the description, the body, provenance (commit + sha256) and one copy-paste command. No login to browse. Hosting is a static host with Git-based CI/CD — **Vercel** is the fit (free Hobby tier; note *commercial* use requires Pro), with **GitHub Pages** as the zero-cost alternative that needs no second service, since the source repo is already on GitHub.
- **What this is not**: no hosted brain, no accounts, no telemetry, no runtime fetch, and no "sign in to unlock the intelligence". The whole marketplace can be deleted and KiCode is unchanged — which is the point.
- **Consequences / phasing**:
  - **A (this ADR)** — decisions recorded; `ROADMAP.md` updated. No code.

## ADR-033: The Agent Learns Without Being Asked
- **Context**: The owner reported "skills not auto-saving". The honest cause was not a bug: `remember` is a tool the *model* chooses to call, so a session only taught the brain when the model happened to think of it — and a model that never thinks of it leaves nothing behind. ADR-031/032 had designed the fix (a second extraction pass) but parked it. The owner chose to build it.
- **Decision**:
  1. **One extra request after a turn, on the user's own provider.** `learnFromSession` asks a single question — "what here is worth keeping?" — over a truncated, tail-weighted transcript, and expects a JSON array of at most five items (a skill, or a project memory). It is a plain request on the user's key; a hosted harness would break the rule that KiCode needs no account and no server.
  2. **It is off the critical path.** The pass runs *after* the turn has ended and is not awaited (`void this.learnAfterTurn(...)`), because it exists to help a **future** session and must never delay the reply the user is reading. A pass that fails is a quiet no-op, never an error card.
  3. **It writes through the tool's own writers, not new ones.** `remember`'s `saveSkill`/`saveMemory` are exported and reused, so slug names, capped bodies and the overwrite refusal are identical. The pass is **additive**: an existing skill is skipped rather than replaced (correcting one stays a deliberate `action: "update"`), and a memory whose text is already recorded is skipped.
  4. **Secrets are refused in the new path too.** `saveMemory` itself had no secret check — only the tool's `run` did — so a secret-shaped item would have been written by an automatic pass with no user in the loop. The check was extracted into `looksLikeSecret` and is now applied in **both** places. This was the only real security gap found while building it.
  5. **A request that cannot help is not made.** A transcript under ~200 characters is a greeting; the provider is never called. A parse that finds no array is a no-op, not an error.
  6. **It is a setting, because it spends money.** `"learning": "auto" | "off"` in `kicode.json`, or `KICODE_LEARNING=off`. On by default: a brain that only fills when the model remembers to call `remember` is the half-built version this exists to finish.
- **Also in this ADR — the plan-mode classifier was too strict.** The owner's "bash error sometimes" was plan mode refusing a command that only reads. Broadened, each case deliberate: assignments in front are stripped (`FOO=bar ls` sets a variable, it does not write); plain filters added (`uniq`, `cut`, `tr`, `nl`, `basename`, `dirname`, `realpath`, `readlink`, `printenv`, `id`, `ps`) while commands that can rewrite their input (`sort -o`, `sed -i`, `tee`, `xargs`) stay out; and `git branch`, `tag`, `remote` and `config` are allowed **only** when they name nothing (`git branch` lists; `git branch feature` creates) or carry a listing flag, with writing flags refused outright. `node -e` and `npm test` remain refused — they run code.
- **Outcome**: 1067 tests across 51 suites, typecheck clean, ESM build 530.91 KB. New coverage: the array is found through a fence and a sentence before it; unusable items are dropped and the result is capped; the transcript labels speakers, omits the system prompt, and keeps its tail; a request is skipped for a transcript with nothing in it; a failed request reports rather than inventing; the brain is created on the first pass and both kinds land; a second pass adds nothing it already knows and does not overwrite a skill; and a secret is refused on the automatic path. Verified against a real brain fixture — the skill file carries frontmatter, the memory carries a dated entry.

## ADR-034: `[Add+]` Puts a Queued Message Into the Turn in Flight
- **Context**: The queue (ADR-028) is right when the next words can wait, and wrong the moment the model is half a step away from the wrong thing: a correction typed to stop it then lands *after* the turn it was meant to steer. The owner asked for a second control on the queued tile — "force the agent [to] listen this new message if click on add" — placed **before** `[x]`, so the space between the two chips belongs to it and a click that lands a column late can only mean "send it now", never "throw it away".
- **Decision**:
  1. **A steer is a message in the transcript, not a new request.** `Agent.steer(text)` holds the words for the loop's next request; it does not call the provider itself. A turn talks to the provider in exactly one place, and a second request fired from a click would race the one already in flight.
  2. **The words wait for a safe seam.** They are appended at the top of the next loop iteration, never where they arrived. A message slipped between an assistant's tool calls and the results that answer them would break the pairing every endpoint insists on; the top of an iteration is the one point where that pairing is always whole.
  3. **A reply already streaming does not end the turn.** `steered` is a high-water mark read before each request. A higher reading afterwards means the model never saw the words — so that reply answered the turn as it stood *before* them, and the turn continues (`continued: { reason: "steered" }`) instead of ending on an answer to the wrong question. Once the words are part of a request the matter is settled: no nudge, no re-ask.
  4. **`steer` reports whether it had anywhere to put them.** It returns `false` with no turn in flight, which is the queue's cue to simply run the message — "now" is the whole promise of the button, and a paused session can hold a queue for a long time. A queued line beginning with `/` keeps its ordinary path: it is an instruction to KiCode, not words for the model, so it cannot ride inside a turn.
  5. **The message leaves the queue as it is steered.** It is spliced out first, so the drain cannot later send it a second time as a turn of its own.
- **Outcome**: `[Add+]` precedes `[x]` on every queued tile, each with its own hit columns. Verified: typecheck clean; 1067 tests across 51 suites (five added — `[Add+]` drawn before `[x]` with a hit box that stops short of the drop chip; a click handing the first queued message to the running turn while the rest stay queued; a mid-reply steer keeping the turn open and appearing on the next request; a steer landing after the tool results it interrupted; and `steer` refused when no turn is running); ESM build 530.91 KB; `--version` 0.1.0.

## ADR-035: A Steer You Can See, a Queue You Can Type At, and When Numbers Are Wrong
- **Context**: A batch of owner reports, three of them the same underlying mistake — a value that was correct in isolation but was being used to answer a question it could not answer.
- **Decision — a steer is visible where the words actually land (finishing ADR-034).** The `continued: { reason: "steered" }` event moved from where the *click* happened to where the words *join the transcript*, which is the top of the loop's next iteration. That is the only point that is true for both cases: a steer that interrupts a reply and a steer that lands while a slow tool is still running. Before this, the second kind was silent — the tile vanished, which reads as a deletion. The TUI now holds its own list of unread steers, and:
  1. the **spinner names the wait**: `thinking… · +1 to read`, cleared when the `steered` event says the model has them;
  2. **a failed or cancelled turn puts them back** at the front of the queue, in order, with a note — they were typed, never read, and nothing else knows they existed. The agent clears its own held steers at the start of every turn for the same reason, so they can never attach to an unrelated later turn;
  3. images travel with them. A steered message is `userContent(text, images)`, not text alone: an attached screenshot is part of what was being said.
- **Decision — the queue is a list the keyboard can work.** A tile's chips need a mouse, and a queue is exactly what someone reaches for with their hands on the keys. The click and the key are the same three acts, deliberately: `ctrl+a` **steers** (the tile's `[Add+]`), `ctrl+x` **drops** (the tile's `[x]`), and `enter` **takes the message back into the prompt to rewrite it** — the one action a chip cannot offer, and most of the reason to look at a queue you cannot change your mind about. The list rebuilds itself after an action (`ctrl+a`/`ctrl+x` stay open) because acting on its own data is what makes a stale row a stale *index*.
  1. Bare `/queue` opens this list rather than printing one; a printout is a dead end you have to retype from.
  2. It is the one command that runs **while a turn is in flight** (`RUNS_WHILE_BUSY`). A message typed during a turn queues behind it, which is right for words the model should read and wrong for a command that only lists: the queue is non-empty *only* while a turn runs, so queueing `/queue` would make it unreachable at the one moment it is useful.
  3. Digits pick a row because the search field is off — on a list this short a number is a faster cursor than an arrow key.
- **Decision — `/compact` means compact.** `planCompaction` returned null whenever the session already sat inside the target, so `/compact` on a session well inside the window said "nothing to compact" and did nothing — the opposite of what asking for it by name means. `CompactionOptions.manual` is now set by `compactNow`, which **lowers** the target to half the session (`min(size, current / 2)`) so the pass cannot refuse, and never raises it, so a session genuinely over the window is compacted exactly as before. A floor (`MIN_MANUAL_TOKENS`, 2 000) keeps a session of greetings from being "summarised" into a briefing that costs more than it saves.
- **Decision — auto-compaction fires at 150K.** `DEFAULT_COMPACT_AT_TOKENS` is 150 000 and `DEFAULT_CONTEXT_TOKENS` is 200 000. The pairing is the point: `shouldCompact` takes `min(window − reserve, compactAt)`, so a window that did not exceed the ceiling would decide instead and the ceiling would never be the number that triggers. `config.test.ts` now asserts `DEFAULT_CONTEXT_TOKENS > DEFAULT_COMPACT_AT_TOKENS` so the two cannot drift back into that.
- **Decision — dates are the user's, not the file's.** Two separate wrongs, both from reusing a stored value as a display one:
  1. `formatSessionDate` fell through to `iso.slice(0, 10)` — the **UTC** day, so a session started last night read as the day before for anyone east of Greenwich, and in a machine format where a person's is wanted. It now counts whole days between two **local midnights** (rounded, so a 23- or 25-hour daylight-saving day is still one day) and renders with `Intl` at `dateStyle: "medium"`, which with no locale named is the system's own.
  2. The month/year group heading was a hardcoded English month list — the one part of a date that cannot be read at a glance by someone whose system is not English. It is now `Intl`'s `{ month: "long", year: "numeric" }`.
  The memory stamp in `remember` had the same UTC bug and is now the local calendar day. It keeps its ISO `YYYY-MM-DD` shape on purpose: that value is data that gets read back and sorted, not something to be shown in a system's own style.
- **Outcome**: typecheck clean; **1074 tests across 51 suites**; ESM build 537.14 KB; `--version` 0.1.0. New coverage: a steer during a tool now reports itself and lands after that tool's result; a steer on the last allowed step is kept rather than lost; `[Add+]` drawn before `[x]` with a hit box that stops short of the drop chip; the spinner naming an unread steer; the queue list opening under `/queue`, dropping with `ctrl+x` and steering with `ctrl+a`; `enter` taking a message back into the prompt and sending it again; `/compact` planning a pass on a session inside the automatic target and never aiming above it; and a session's date rendered rather than printed as its stored ISO stamp. The 13 tests that had pinned 128 000/100 000 as literals now read the constants, so the defaults are stated once.

## ADR-036: A Stamp Is Not a Date, Tracked Work Outlives the Tools, and a Key Cannot Arrive Quietly
- **Context**: Four owner reports, and one thing found while answering them. Two of the four were the same mistake ADR-035 named — a stored value used to answer a question it could not answer — which is why they are recorded together rather than one at a time.
- **Decision — a stored stamp is never printed.** The `[USAGE]` card read `session started 2026-10-02T05:38:58.828Z`: the record's own field, in **UTC**, in a machine's shape. It was wrong twice over — the hour was off for everyone not on UTC, and a timestamp is not something a person reads. `formatStamp` now renders `DD-MM-YYYY HH:mm` from the local clock, and `createdAt` is only ever formatted, never interpolated. The format is written out rather than handed to `Intl`, superseding ADR-035's `dateStyle` for absolute moments: the earlier decision took "the user's own system format" as the goal, the owner has since named the format they actually want, and one shape used everywhere beats a locale that renders differently per machine. The relative words stay — `today`, `yesterday`, `4d ago`, `0 min ago` — because those are not date formats.
- **Decision — the TODO chip reads its own transcript.** The plan tools keep their list in memory and are built fresh with every agent, so a session that was *reopened* — switched back to, resumed in a new process, or rebuilt because the model changed — had nothing tracked as far as the chip could tell, while the checklist sat in the conversation. That is the "`[TODO]` sometimes not showing": the work was never lost, the button could not see it. `planFromHistory(messages, cwd)` replays the transcript's `todo` and `goal` calls through a fresh toolset and returns a snapshot — **exact, not approximate**, because both tools only ever mutate their own state and neither touches a file. It runs wherever a new agent is built from a history, which is the same place the divergence existed: the chip used to keep showing a list the rebuilt agent no longer had.
  1. Only tools that expose a `snapshot` are replayed, so a `bash` call in the transcript is never run again.
  2. A call whose arguments do not parse is **history, not an instruction**: it is skipped, and replaying a transcript can never throw.
  3. The replay is not awaited, and the test that replays a real transcript is what keeps that safe — both bodies mutate before returning, so an `await` added later fails there rather than silently rebuilding half a list.
- **Decision — a key cannot arrive quietly.** `scripts/check-secrets.mjs` scans what is **staged** for the prefixes real providers issue (private keys, OpenAI/Anthropic, GitHub, AWS, Google, Slack, Stripe, SendGrid, JWT, and this project's own OpenCode/Experiential Labs/Kenari shapes) and refuses the commit, naming the file, the line and the pattern. `.githooks/pre-commit` runs it, so the fast path is a clone that ran one command; **CI runs the same check over every tracked file**, so a clone that never did is covered anyway. That ordering is the point of running it *before* typecheck in CI: a key in a commit has to be rotated, and the fewer commits it has to be taken out of, the better.
  1. It is a shape check, not a scanner, and it says so. A value it cannot recognise is one it will not stop — the real guard is never having the key in a shell that commits.
  2. A fixture that must contain one of these shapes carries `kicode-secret-ok` **on the matching line**. Per-line rather than per-file on purpose: a file-wide marker is somewhere a real key could hide. Three existing fixtures needed it, and marking them was the reviewable act it is meant to be.
  3. A value is never echoed whole — a masked prefix and the line number are enough to find it, and not enough to use it.
- **Also — the timing tests are no longer a bet on the machine.** One full-suite run failed three TUI tests that passed on the next run with identical code: fixed sleeps under a fifty-file parallel run are a bet on how fast the host is, and CI runs on shared runners — exactly the conditions that produce them. The queue tests now use a deliberately wide busy window (the thing they need is a turn still running when the next prompt arrives, which is the one thing a loaded machine cannot be trusted to hold to), and the clipboard test waits for the screen to say something rather than guessing how long that takes. The suite is slower by a few seconds and no longer fails for reasons that have nothing to do with the code.
- **Decision — `/learn` and `/memory`, so the brain can be inspected without a file browser.** `learn` runs the extraction pass **and waits**, reporting what landed and what was skipped: the automatic pass is silent by design — it exists to help a future session — so "nothing was added" is a thing only an explicit request can tell you, and an explicit request ignores `learning: "off"` because that setting is about the pass that runs on its own. `memory` prints where the brain is, whether this directory has a memory file, the memory text the agent is actually handed, and the other projects recorded; `memory full` adds the skill list. Its output is deliberately short and its reference lines go **last**: every transcript entry costs two rows, and a command whose own answer scrolls off the top has told you nothing.
- **Outcome**: typecheck clean; **1083 tests across 51 suites**; ESM build 543.28 KB; `--version` 0.1.0. Verified against the bundled mock provider with the real binary: `node dist/cli.js -p` completes a request, runs a tool, survives a missing file and a refused gated tool, and answers — and `--all` mode of the secret check is clean over the whole tree. New coverage: the replay rebuilds a checklist and ignores cleared, malformed and unrelated calls; the chip appears when a session is switched back to; `/memory` reads a brain from `KI_BRAIN_PATH` and shows the memory itself; `/learn` reports what it kept, what it skipped, and refuses an empty session; and the defaults compact at 150K and not at 149K.

## ADR-037: The Package Is Publishable, the License Is Proprietary, and the Bundle Is Minified
- **Context**: The owner asked whether putting KiCode on npm means showing all of the work to everyone. The two questions underneath — "does publishing publish my repository?" and "can someone read what I ship?" — have different answers, and the second one was, at the time, "yes, all of it": the bundle was un-minified and each section still carried its `// src/agent/brain.ts` marker, and the licence was MIT, which grants exactly the rights the owner was worried about. Distribution, licence and artifact shape are one decision, so they are recorded together.
- **Decision — npm is a channel, not a licence.** Publishing to the registry uploads a tarball, not the repository, and the two are deliberately kept apart:
  1. **Public npm, private repository.** `files` ships `dist`, `README.md` and `CHANGELOG.md`; npm always adds `LICENSE` and `package.json` regardless. Source, tests, these ADRs and the git history never reach the registry, and no `repository` field is set, so the package page points nowhere at all. The secret is the repository; the artifact is merely visible.
  2. **`private: true` is gone** so `npm publish` is possible at all, and `prepare` still builds `dist` so a published tarball is never stale. `CHANGELOG.md` was added to `files` because npm does not include it automatically — README and LICENSE it does.
  3. **The licence is the protection, not the packing.** `MIT` became `UNLICENSED`, and the MIT text was replaced by an all-rights-reserved licence that permits installing and using a copy for personal or internal business purposes while forbidding copying, redistribution, sublicensing, selling and reverse engineering. Before this, publishing was an *invitation*: MIT says "use, copy, modify … sublicense, and/or sell".
- **Decision — a minified bundle, with the ceiling named.** `minify: true`, plus `legalComments: "none"` to drop `@license`/`@preserve` banners as well — set through `esbuildOptions`, because that option belongs to esbuild and not to tsup, which the typecheck was the first to say. The shipped bundle fell from **543.28 KB to 291.51 KB** and the `// src/…` markers are gone. The decision states its own limit on purpose: this **raises the bar and is not a secret** — a bundle is readable by anyone determined to read it, and it is the licence, not the minifier, that forbids copying. A standalone binary was considered and deliberately left for later; it is the next step only if the bar needs to be higher.
- **Outcome**: typecheck clean; **1083 tests across 51 suites**; minified ESM build **291.51 KB**; `--version` 0.1.0. The tarball is 5 files — `CHANGELOG.md`, `LICENSE`, `README.md`, `dist/cli.js`, `package.json` — at 125.0 kB (370.5 kB unpacked), with no `.env`, no secrets and no source; installed into a clean prefix it runs (`kicode --version` → 0.1.0, `--help` ok); and the minified bundle was verified against the bundled mock provider, where a one-shot turn reads a file and answers correctly.

## ADR-038: A First Run Someone Can Finish, and a Key That Is Never Written
- **Context**: A first-run audit — a genuinely empty environment, an empty project directory, and the packaged binary — found four things, and three of them were the same mistake wearing different clothes: a promise the code did not keep. The starting point was the owner's own `~/.kicode/kicode.json`, found holding **six live keys in cleartext** while four separate places in the product said that could not happen.
- **Decision — the key is never written, and a key found in a file is refused.** The claim was already written down four times — the README ("there is no write path for one — nothing to leak and nothing to accidentally commit"), `USAGE` ("the file has no place for a key"), the header comment on `config.ts`, and the note `--init` prints ("the key stays in the environment") — and the code contradicted all four.
  1. **Nothing writes one.** `settings-write.ts` writes `baseUrl`, `apiKeyEnv` and `models`, and its provider parameter no longer has a field for a key, so a caller cannot pass one by accident. `/key` and `/connect` still take a key; it is held **in memory** for the session (the `endpoints` map, which is what the agent is built from) and the note now names the environment variable that would make it permanent rather than saying "saved".
  2. **One found in a file is reported and ignored, at every scope.** `settings-file.ts` already refused an inline key at *project* scope and already recorded it as a warning, but it *used* a key at global scope and read a **provider-level** `apiKey` without a word — and the provider block is where all six of them were. The rule the module's own doc comment described ("a key found here is reported and ignored") is now the rule it implements, and the warning names the variable to set instead. The endpoint is still read: only the credential is dropped.
  3. The distinction the three claims were reaching for is worth stating plainly: a file on your own disk is not more private than one in a repository — it is just as easy to sync, back up, or paste into an issue. So there is no scope where a key in a file is acceptable, and `apiKeyEnv` is the only way an endpoint carries a credential.
  4. **This is a migration, not just a fix.** Keys previously stored inline stop working. The warning is the migration path and it is one step: set the named variable. Reported rather than silently dropped for exactly that reason.
- **Decision — a missing key opens the UI instead of refusing to start.** `validateConfig` runs before the full-screen UI, so the one moment the UI's own remedies were unreachable was the one moment they existed for: `/connect` declares an endpoint and `/key` takes a key, both inside the screen that a user without a key could never reach. When the UI is about to run and the missing key is the only problem, the run now continues and the UI opens with the problem shown as a warning (`TuiOptions.notice`). A run that cannot show a UI — a pipe, or `-p` — still stops with exit code 1 and the environment hint, because there is nobody there to read a screen.
- **Decision — `--tui-preview` is exempt from the config check.** It draws one frame and exits, needs no credential, and is what someone runs **when KiCode is misbehaving** — so a tool for debugging the broken case was unavailable in the broken case. It joins `--init`, which was already exempt for the same reason.
- **Decision — the two defaults are a pair.** `DEFAULT_MODEL` was `deepseek-v4-flash` against `DEFAULT_BASE_URL` of `https://api.openai.com/v1`: following the product's own setup hint with an OpenAI key produced a model-not-found on the very first request. `deepseek-v4-flash` is the bundled mock's model, which is how it came to sit under an OpenAI default. The model is now `gpt-4o-mini`, and `config.test.ts` pins the host and the model prefix together so they cannot drift apart again.
- **Also — this is what the audit was for.** The two failures the owner had actually seen (a queued tile with no `[Add+]`, a raw UTC stamp) turned out to be a stale binary, not a bug: the global `kicode` is `npm link`ed at this checkout, and the run in the screenshot predated the rebuild. Auditing instead of guessing is what surfaced the four real ones above.
- **Outcome**: typecheck clean; **1088 tests across 51 suites**; minified ESM build 292.12 KB; `--version` 0.1.0. New coverage: a provider-level key is refused at both scopes and names its variable; a top-level key in the global file is refused as well; the default endpoint and model are asserted as a pair; `--tui-preview` exits 0 with no key at all; a one-shot run with no key still exits 1 with the hint; and the UI shows the notice it was handed on the screen it opens.

## ADR-039: A Turn Is Not Cut Short, a Key Is Not the Only Way In, and a Ceiling You Can Move
- **Context**: Five things from the owner, in the round before release. Three were limits that had been set once and never revisited, one was a missing action, and one was the approval prompt doing its job so often that its job had stopped mattering.
- **Decision — a session switch waits for the turn instead of killing it.** *(Superseded by ADR-040: the switch no longer waits, because the turn now runs in the background.)* The TUI holds one agent and one busy row, and `switchSession`/`newSession` rebuild the agent. A running turn holds the *old* agent in a local variable and its loop did `if (this.sessionId !== turnSession) break` — and breaking a `for await` closes the generator, which cancels the in-flight request. So clicking another tab, or opening a new session, **threw away the work the other session was doing**; the comment above it called this "let the abandoned turn go", but from the outside it is the agent being stopped by a session it has nothing to do with.
  1. The turn now records itself as a `running` promise, and `settleTurns()` awaits it in `switchSession` and `newSession` before either proceeds. The turn finishes and saves into **its own** session, and the switch happens after — a turn belongs to the session that started it, so the switch is what gives way.
  2. The wait is visible — `a turn is still running — switching when it finishes` — because a click that appears to do nothing is worse than a click that says why it is waiting.
  3. It loops rather than awaiting once: a finished turn may drain a queued prompt into another, and that turn is just as unswitchable.
  4. Deliberately **not** full background turns. Running two sessions' agents at once means per-session entries, queues, plans and saves, which is a different feature; this is the smallest thing that cannot lose work. The `sessionId !== turnSession` guard stays as a backstop for the paths that do not go through a switch.
- **Decision — Shift+Enter breaks the line, from every encoding a terminal might use.** It could not work before for a concrete reason: `keys.ts` mapped `\r` and `\n` to `enter`, the `Key` type had no modifier, and nothing ever asked the terminal to report one — so Shift+Enter arrived as a plain Enter everywhere.
  1. **Ask for it.** `CSI > 4 ; 2 m` (modifyOtherKeys level 2) on the way in and level 0 on the way out, in the same write as the mouse and paste modes. A terminal that does not know the sequence ignores it, so asking costs nothing where it is unsupported.
  2. **Accept both encodings regardless** of which was enabled — `CSI 27 ; m ; code ~` and kitty's `CSI code ; m u` — so a terminal already in a reporting mode, or a multiplexer adding its own layer, still lands on the right key rather than an unknown sequence. `:` joins the parameter class for the event-type suffix, without which `CSI 13;2:1u` failed to match at all and spilled into the prompt as the text `[13;2:1u`.
  3. **Put the other keys back where they were.** Enter with ctrl is `ctrl+j`, a modified letter goes back to `ctrl`/`alt`, shift+Tab stays shift+Tab — a terminal switched into a reporting mode must not quietly break every ctrl binding.
  4. **A newline is not `insert`.** `LineEditor.insert` flattens newlines so a pasted prompt cannot submit itself, and that rule must not be loosened for the one key whose meaning is "break here": `insertNewline()` is its own method, and `breakRows` now ends a row at a `\n` so the break is drawn instead of rendering as a zero-width gap.
- **Decision — the turn ceiling is settable, and higher.** `maxTurns` was `overrides.maxTurns ?? DEFAULT_MAX_TURNS` with **no file key and no environment variable**, so a long task that hit it could only be continued by sending another message — a fresh turn with a fresh allowance. It is now `kicode.json` `maxTurns`, then `KICODE_MAX_TURNS`, then a default raised from 40 to 100 (ordinary work had already outgrown 12, and the message is a stop, not a failure).
- **Decision — the approval prompt stops asking about reading.** `bash` is gated, so every call prompted, and `[a] always was remembered in the **agent** — which is rebuilt for every model switch, `/cd`, session switch and mode change, so "always" meant "until something unrelated happens".
  1. **"Always" lives on the app.** `approvedTools` outlives the agent, and `approver()` answers `always` without opening a modal for a tool already answered. Per run rather than per session: the answer is about the tool, and being asked again by a tab just opened is the annoyance it exists to remove.
  2. **Read-only calls do not prompt, in either mode.** `readsOnly` is no longer conditioned on plan mode — reading a file is as harmless in build mode, and the tool's own conservative classifier is what decides. This is the same trust the classifier already carried: plan mode *allowed* a read-only command to run.
  3. **`allow` in `kicode.json`** names prefixes that skip the prompt per tool, checked by `loop.ts` through an injected predicate so the policy stays with the config and the loop only knows to ask. The match is deliberately literal: `git status; rm -rf /` begins with a rule and is a different command, so a value carrying a shell control character never matches. A wrong rule costs a prompt; it cannot cost a silent write.
- **Decision — a skill can be retired, into the trash.** Skills are folders with a `SKILL.md` in them and there was **no delete path anywhere** — only `/skills` to read and `remember action:"update"` to correct. `/skills delete <name>` moves the skill's **own** folder to `<brain>/.trash/`, stamped, and reports where it went.
  1. The move is driven by the file path the index returns, never by rebuilding `<brain>/skills/<name>` from the name: `readSkillIndex` walks nested categories, so a rebuilt path would move the whole category and leave the skill.
  2. Trash rather than `rm -rf`: a wrong name is a move back, not a lost afternoon. The scan reads `<brain>/skills` only, so the retirement takes effect at once.
  3. The mention index is dropped afterwards — it is cached for a minute and every `@skill:` and `/skills` read goes through it, so without that the skill would still be offered after being retired.
- **Outcome**: typecheck clean; **1103 tests across 52 suites**; minified ESM build 295.97 KB; `--version` 0.1.0. New coverage: a switch made under a running turn defers and the turn's session keeps its answer; a modified key sequence is held until whole; Shift+Enter decodes from `CSI 27;2;13~`, `CSI 13;2u`, `CSI 13;2:1u`, `ESC CR` and `ESC LF`, while unmodified Enter still submits; ctrl and alt still arrive through a reporting mode; a line break keeps a row of its own while a pasted one is still flattened; `maxTurns` comes from the file then the environment and nonsense is ignored; the `allow` predicate refuses anything that chains or redirects; and a retired skill leaves the index while its category survives.

## ADR-040: A Turn Runs in Its Own Session, So Another Session Can Be Used While It Does
- **Context**: ADR-039 made a session switch *wait* for a running turn — a deliberate stopgap that named its own limit: "deliberately **not** full background turns. Running two sessions' agents at once means per-session entries, queues, plans and saves, which is a different feature." The owner asked for that feature: "so I can work in another session while one runs." The consequence of the stopgap was that a long turn made every other tab unusable, which is the opposite of what tabs are for.
- **Decision — a session is parked, not waited for.** A turn belongs to the session that started it, and state a turn writes to is resolved **per event** rather than captured once, because the user may leave mid-turn. When the user switches away, `parkCurrent()` stores the session's `agent`, `entries`, `plan`, `busy`, `queuedPrompts`, `steering`, `recovery`, `createdAt`, `title` and `isPaused` in a `parked` map — **by reference, never by copy** — so a turn already running goes on appending to the very array the user will find on return. `switchSession`/`newSession` no longer call the (now deleted) `settleTurns`; they park, save, and move at once.
  1. `runTurn` takes an optional `sessionId` (defaulting to the session on screen) and branches on `isCurrent(sessionId)` for each event: on screen it writes the live fields, off screen it writes `parkedState(sessionId)`. Removing the old `if (this.sessionId !== turnSession) break` is the fix — breaking a `for await` closed the generator and cancelled the request.
  2. `running` became a `Map<string, Promise<void>>`, one promise per session, because a background turn and the one on screen are both live at once.
  3. **A background turn saves its own session.** `saveParked(id, state)` writes the turn's own agent under the turn's own id, so the answer is on disk even if the user never goes back to look; `shutdown` also saves every parked session before exiting.
  4. **Coming back is exact, and instant.** `unpark` restores the parked state (including the agent, so a still-running turn keeps the same one) instead of reloading from disk, and re-raises the spinner if the turn is still busy. A tab with a turn running in it is marked `◐` — otherwise a session working behind the current one is invisible.
- **Decision — a background turn cannot put a card on screen.** The approver and the asker are now **bound to the session they were built for** (`approver(this.sessionId)`, `asker(this.sessionId)`), so a callback firing for a parked session knows it is off screen rather than reading whichever session happens to be current.
  1. **Approval is auto-denied and said once** (`<session> — <tool> needs approval, denied`). The alternatives were worse: a modal would hijack the session the user is actually in, and pausing on an approval nothing can answer makes the background turn look hung. The owner chose this over "jump to that session" and "queue until visited".
  2. **A question is skipped**, answered as dismissed, and the turn carries on with no answer. Same reasoning: there is no screen to show it on.
  3. **A failure is news, not a card.** A background turn that throws gets a warning notice (`<session> — turn failed: …`) rather than a recovery modal, for the same reason the modal exists at all — it asks a decision, and there is nobody in that session to make it.
- **Decision — a background queue is worked through.** The owner chose auto-drain, so a parked session whose turn ends shifts its next queued prompt and runs it, and so on, unattended. One exception: a queued **slash command** in a parked session is left queued with a notice (`a queued command is waiting for you`), because a command acts on the screen it was typed in and running one against another transcript is the leak this design exists to prevent.
- **Decision — a session keeps its own settings, not the screen's.** The trade-off above was closed in follow-up work: `model`, `baseUrl`, `cwd`, `mode` and `variant` are now part of `ParkedSession`, stored when a session is left and restored when it is returned to. `/models`, `/cd`, Shift+Tab and `/variants` therefore stop being changes to "the app" and become changes to the conversation — which is what a per-session setting is for.
  1. **Reference for the arrays, value for the scalars.** `entries`, `queuedPrompts` and `steering` keep the shared-object trick (a running turn must go on writing to the same array); `model`, `baseUrl`, `cwd`, `mode` and `variant` are simply copied at park time and put back at unpark. The parked agent was built with them, so nothing is rebuilt on return — restoring the fields is enough to keep the screen honest.
  2. **The directory is the one that has to do something.** `cwd` is not only a label: the `@` index and the session tab bar are per directory. `unpark` notices a moved directory and rebuilds both, exactly as `/cd` does.
  3. **Persistence where the store already had it.** `SessionRecord` already carried `model` and `baseUrl`, but the TUI never passed its own — every save wrote `config.model` instead, so the field was always the default. `saveSession` now takes the session's `model`/`baseUrl` and falls back to the configured pair only for a session that has none; `SessionSummary` gained `baseUrl`, so a switch to an existing session comes back on the model it was using. That is also what makes the setting survive a restart for a session you return to.
  4. **Mode and variant are recorded too.** They joined `model`/`baseUrl` in the session file — `SessionRecord` gained optional `mode`/`variant`, so a record written before them still reads — and `run.ts` now carries a resumed session's model, endpoint, mode and variant out of the resume block and into the TUI's options. `--continue` therefore opens the conversation in the mode and variant it was saved in rather than in the defaults, which is what "survives a restart" has to mean. `TuiOptions` gained `mode`/`variant` for that; `mode` is validated on the way in (it must be `build` or `plan`) so a hand-edited file cannot put the app in a mode it does not have, while a variant is taken as written because the valid set belongs to the model.
  5. **A fresh session inherits.** A new session, and a session loaded from disk for the first time before this change existed, start from what is on screen. The first time it is parked, it keeps what it had from then on — so the change is additive to the behaviour that was already there.
- **Edge cases found in review, and fixed.** Three holes turned up in the park/unpark paths, all of them about a turn outliving a change of identity:
  1. **`/fork` moved the id without parking.** A turn running in the forked-from session would, mid-turn, see itself as "not the current session" and write into a `parkedState` invented after `this.agent` had already been rebuilt — so its events went to an empty transcript owned by the *fork's* agent. `/fork` now parks first, before the id and the agent move.
  2. **Deleting the session on screen did not stop its turn.** `deleteSession` cancelled `this.parked.get(id)`, but the current session is not parked, so the live turn ran to completion against a file with no future. The live agent is cancelled too when the deleted id is the current one.
  3. **A notice about a closed tab named a raw id.** `sessionLabel` read only the tab bar; a closed (or being-deleted) session has no tab left, so the notice fell back to something like `2026-10-02T…-a1b2c3 — turn finished`. It now consults the parked title as well.
- **Edge cases in the background state itself, from the same review.** Four more, all state that belonged to a session but was held for the whole app:
  1. **A goal was a flag, not a session.** `goalRun` was one boolean. A `/goal` running in one session made *every other* session's pill read `[GOAL]` and suppressed *its* recovery card — and because only the on-screen branch cleared it, a goal session that was backgrounded stayed stuck as Goal for the rest of the run. It is now `goals: Set<sessionId>`, cleared for its own session in both branches of the turn's `finally`.
  2. **A pause was ignored off screen.** The background drain ran a departed session's queue without consulting its `isPaused`, so leaving a paused session released the message the pause was holding. A pause is a decision wherever the user is looking, so the drain checks it now.
  3. **`steering` was not reset on a new session.** `resetSessionState` cleared the queue and the plan but not `steering`, so a new session shared the *same array* a parked session's running turn was still consuming — which could show a count that was not its own, or file another session's unread messages into its own queue. It is a fresh array now.
  4. **`stopping` was global too.** Ctrl+C in one session and then switching cleared the flag out from under the turn still winding down. It is parked and restored with the session, and the background branch clears it when the turn ends.
- **Outcome**: typecheck clean; **1116 tests across 52 suites**; minified ESM build 300.33 KB; `--version` 0.1.0; secrets check clean. New coverage: a turn left running in a session keeps going when a new session is opened (the switch does not wait, and the tab shows `◐`); the turn's answer is still saved under its own session; a queued prompt in a departed session drains on its own while the user stays in the new one; an off-screen approval is denied without ever drawing a card; an off-screen question is dismissed rather than shown; a parked session keeps its own mode when another session changes its own; a parked session keeps its own directory (`/cd` in one does not move the other); a session switched to from disk comes back on its own model, endpoint, mode and variant; the store round-trips `mode`/`variant` while a record written without them reads back with neither; **`runCli` driving the real `runTui` (mocked) resumes a session on its saved model, endpoint, mode and variant** — the restart path, tested end to end at the seam that assembles the options; deleting the session on screen stops its running turn; and closing its tab keeps the answer rather than throwing it away; only the session running a goal is marked Goal, and it stops being one when the goal ends off screen; and a paused session does not drain its queue while it is in the background. The existing `/fork` test was updated to look for the fork's own save rather than the last one overall, since the forked-from session is now parked and flushed on the way out. Testing the approval and question paths needed the harness itself fixed — its fake agent read a single shared approve/ask pair that every rebuild overwrote, so an agent now keeps the channels it was built with, which is what the real app does and what makes the sessions genuinely independent. One pre-existing fixed-sleep test (`/skills <name>`, a 60 ms bet on how loaded the machine is) was de-flaked to poll like its neighbours while this was being verified. Also wired the **kitty keyboard protocol** (`CSI > 1 u` / `CSI < u`) alongside `modifyOtherKeys`, and proved an inline `apiKey` already on a provider entry survives an `addGlobalProvider` rewrite (nothing KiCode writes *adds* a key, but rewriting an entry must not destroy one).

## ADR-041: A Provider Is Declared, Never Inherited
- **Context**: The owner installed the published package on a machine where `OPENAI_API_KEY` and `OPENAI_BASE_URL` were set as Windows **user** environment variables — inherited by every process, including a shell in a brand-new directory with an empty `KICODE_HOME`. KiCode started working with nothing configured, and the owner's question was the right one: *"i did not config the opencode then how it work? maybe its using global data"*. It was not global data — KiCode stores no key at all. `loadConfig` fell back to `env.KICODE_BASE_URL ?? env.OPENAI_BASE_URL ?? DEFAULT_BASE_URL` for the endpoint and `env.KICODE_API_KEY ?? env.OPENAI_API_KEY` for the key, so an ambient pair belonging to some other tool *became* the session's provider. The source even said so — *"an ambient variable like `OPENAI_BASE_URL` is usually there for some other tool, and silently redirecting KiCode to a different gateway is a confusing failure"* — but its only defence was "a config file beats the environment", which does nothing when there is no config file. The owner's ruling: **a first install must not present a provider; the user configures their own api and providers.**
- **Decision — the environment cannot call an endpoint into existence.** `readProviders` still reads each declared provider's key from its own `apiKeyEnv`, which is the whole BYOK bargain (the key is the one thing KiCode will not keep on disk). What is gone is the fallback that *creates* a provider: the endpoint chain ends at `chosen.baseUrl` with `""` beyond it, and the key chain at `chosen.apiKey`. A key in the environment is now only ever read **because a provider asked for it by name** — declaration, not accident of the shell. `KICODE_PROVIDER`, `KICODE_MODEL` and the other non-credential settings are untouched; it is endpoints and keys that must be declared.
- **Decision — one declared provider is used without being named.** `addService` writes a `providers` entry and deliberately does *not* write `provider`, so without this rule `/connect` would leave a session configured and still unstartable. When nothing names a provider and exactly one is declared, it is the one in use. The rule is deliberately narrow: if a name *was* given and did not match, nothing is auto-picked, because silently falling back on a typo hides the mistake — the session reports `No provider is selected` instead.
- **Decision — there is no default endpoint.** `DEFAULT_BASE_URL` is deleted rather than kept as an unused constant, because an exported "default endpoint" that nothing defaults to is an invitation to reinstate the behaviour this ADR removes. `DEFAULT_MODEL` stays — a model is not a credential, and the endpoint's own `/models` list remains the authority. `--base-url`/`--api-key` still configure one run (`run.ts` keeps a `--base-url` endpoint visible in the provider list, so the session never looks like it is on nothing), and `baseUrl` in `kicode.json` still pins a project.
- **Decision — the failure states stay distinct.** `validateConfig` reports no endpoint (`No provider is configured yet.`), an endpoint with no provider selected (`No provider is selected — name the one to use with "provider" in kicode.json.`), and a declared provider with no key (`No API key for provider "x" — set X_KEY.`). Collapsing them would send someone to fix the wrong thing — which is precisely how `export KICODE_API_KEY=…` came to look like configuration for a session that had no endpoint to use it on. For the same reason `noProviderHint` names `/connect` and the two flags rather than a variable: with nothing declared there is no variable to name.
- **Decision — the UI opens anyway, and says what is missing.** A missing endpoint joins a missing key as something the UI can fix by itself (`/connect` is inside it), so the run continues with a notice rather than exiting; a piped or `-p` run still exits 1 with the hint, and `--tui-preview` is still exempt.
- **Outcome**: typecheck clean; **1118 tests across 52 suites**. `config.test.ts` now pins the inverse of what it used to — an empty environment declares no endpoint at all, and an ambient `OPENAI_API_KEY`/`OPENAI_BASE_URL` pair supplies nothing unless a provider names one of them. The `run.test.ts` harness declares its mock provider the way a user would (a `providers` block in the global file, with the key in a variable of its own), which is what makes the rest of that suite a test of the supported path rather than of the env fallback; new coverage asserts the two first-run messages, including `Set ACME_API_KEY and try again` for a declared provider with no key. `init.test.ts` pins that `--init` records an endpoint when there is one and records nothing when there is not. Verified against a clean prefix: with `OPENAI_API_KEY`/`OPENAI_BASE_URL`/`TOKENHARBOR_API_KEY` set in the *surrounding shell* and an empty `KICODE_HOME`, the run refuses with `No provider is configured yet.` and the `/connect` remedy, where 0.1.0 would have started a session against the ambient gateway.

## ADR-042: KiCode Reads the Skills Others Install
- **Context**: ADR-032 drew the seam but left it unbuilt: the `npx skills` CLI installs into `.agents/skills/` (project level, and `~/.agents/skills/` for the user), and KiCode only read its own brain — an installed set sat on disk invisible to the briefing, `recall`, `@skill:` and `/skills`. This is Phase B of that ADR: read what the CLI writes. (Phase C — a first-class `kicode` entry in the CLI's agent table — stays upstream.)
- **Decision — an ordered list of roots, one reader each side.** `skillRoots()` names them: the brain's `skills/` first, then `<cwd>/.agents/skills/`, then `~/.agents/skills/`. Both the sync reader (`brain.ts`, for the briefing and `recall`) and the async one (`mentions`, for completions, `/skills` and expansion) walk the same roots with the same rules: frontmatter only, shared caps, and the first root wins a name — so a learned skill shadows an installed one of the same name, and the project's shadows the user's.
- **Decision — provenance is shown everywhere a skill is named.** A skill carries `learned` or `installed` from the root it was found in: the briefing and `recall` mark installed rows, `/skills` trails each row with its source, `@skill:` completions say so, and a miss inventory lists the two groups apart. A skill's origin is the thing that decides what may happen to it, so it is never implied.
- **Decision — installed roots are read-only.** Nothing writes there: `remember` still writes the brain, and `/skills delete` refuses an installed name with the path to remove by hand — retiring one here would fight the installer over a folder it manages. The trust rules from ADR-032 stand: a body is model context, never executed, and `/skills <name>` shows it before anything is acted on.
- **Outcome**: typecheck clean; full suite green (new coverage: root order with and without a brain, merged index with first-wins dedup, completion markers, briefing/recall/inventory provenance, `/skills` trailings and the delete refusal). Verified live: a skill dropped into a project's `.agents/skills/` completes after `@`, expands into context on submit, and is recalled by name — with no brain anywhere on the machine.

## ADR-043: A Pasted Key Is Kept, So the Next Run Does Not Ask Again
- **Context**: ADR-038 made the key memory-only — `/key` worked for the session and then the next run asked again, with a hand-set environment variable as the only way out. On Windows that means `setx` plus a new terminal, which is exactly the kind of setup that never gets done: the owner pasted the key every single run. The repo stays private and the machine is the owner's own, so a key at rest in the home directory is the easy default, not a leak.
- **Decision — `~/.kicode/keys.json`, named by variable.** `src/keys-file.ts` reads and writes one object (`OPENCODE_API_KEY` to key, and so on), merged on write and read with `KICODE_HOME` honoured so tests stay hermetic. At startup `run.ts` fills only the gaps: a variable the shell already sets wins, the stored copy is ignored for the run rather than overwriting it. `/key`, `/connect` with a pasted key, and a custom provider with a key all persist through the same writer; pasting again overwrites a rotated key, deleting the file forgets. The declaration in `kicode.json` still carries no key — only the variable name — so the config stays safe to show and copy.
- **Decision — owner-only bytes, atomic write.** Creation mode `0600`, tmp-and-rename like `settings-write.ts`, corrupt-or-foreign content reads as no keys rather than failing the run. The secret-scan hook is untouched on purpose: it covers staged and tracked files, and this file lives in the home directory, never in a repo.
- **Outcome**: typecheck clean; full suite green (9 new `keys-file` tests: round trip, merge, rotation overwrite, refusal of bad names and empty keys, corrupt-file tolerance, non-string entries skipped, `kicode.json` untouched). `/key` now answers with where the key is kept and that it works now and from the next run.

## ADR-044: A Slow Disk Must Not Hold the Panel, and a Quiet Summariser Must Not Hold the CLI
- **Context**: two hangs from the same root cause — a UI gesture awaiting a slow operation on the only thread that reads keys. (1) Every `/settings` arrow press awaited a full config-file write, so the panel felt stuck and a slow disk made it worse with every step. (2) `/compact` awaited the summariser with no busy label, no signal and no way out: the input loop was inside the request, so Ctrl+C was never read and a quiet gateway hung the CLI forever. It also never saved, so a manual compaction was lost on resume.
- **Decision — the screen moves first, the slow work follows.** Settings values (and the theme with them) are adopted before `applyView` returns; the write runs behind and coalesces — ten fast steps land as one write of where they ended — with a shutdown flush for a change stepped moments before quitting. `/compact` runs in the background behind a `compacting…` spinner: a second run is refused, a mid-turn run waits its turn, success saves the compacted transcript (a no-op run writes nothing), and the signal threads `compactNow → summarise → compactMessages → provider.stream`, so the first Ctrl+C aborts the summariser and says `compaction stopped` instead of quitting.
- **Outcome**: typecheck clean; full suite green (2 new tests: a 200ms write still applies the theme within 30ms and saves behind; a hanging summariser shows `compacting`, aborts on Ctrl+C and reports it).

## ADR-052: Every Palette Is Matte
- **Context**: The request was for backgrounds that read as relaxing and clean. Measured against the roster, the problem was specific: several palettes carried real chroma in their fills (`dark` 14% in `input`, `solarized-dark` 30% in `input`, `nord` 12%), and a background is the largest area on screen — colour in it is read as colour everywhere at once, which is what makes a screen tiring rather than calm. Two palettes also failed on the other half of "clean": `tokyo-night`'s panel sat 8 luminance points off its own background, and `catppuccin`'s panel was *darker* than its background while every other dark theme stepped lighter.

Each fill keeps its hue but is desaturated toward equal-luminance grey until its chroma is at most a trace, then scaled to a lightness that guarantees a visible step — 12 points between fills on dark themes, 7 on light. Matte is not greyscale: gruvbox stays warm, nord stays blue, solarized stays teal, and `mono`/`contrast` are held at zero chroma. Two new tests hold the rule for every palette, so a theme added later cannot quietly reintroduce glare or a fill that has vanished into its own background.
- **Outcome**: typecheck clean; full suite green (matte + ladder tests across all 14 themes; the light-theme frame test now reads the colour off the theme instead of a typed-in literal).




## ADR-053: Subagents Are Read-Only Children, Delegated With One `delegate` Tool
- **Context**: The main agent had no way to widen its own reach. Broad work - "where is retry handled", "audit every call site of X" - cost the parent's context, because the only way to answer it was for the parent to read the files itself. Hermes (MIT) solves this with a `delegate_task` tool; its design was read and reused with attribution. Two of Hermes' choices were **rejected** for KiCode: worktree isolation (Git `worktrees` is not in KiCode's toolset, so a write-capable child would be editing the live tree with no way back) and background-by-default delivery (nothing durable reads a result later, and the loop's sequential tool loop has nowhere to put it).
- **Decision**. One `delegate` tool, **no roles** - a role enum plus a per-role model is a settings surface nobody gets right, and a single `delegation.model`/`baseUrl` pin is one thing to configure. The pin defaults to *empty*, meaning the children inherit the parent's model, so a fresh install spends no second model's money until someone names a cheaper one.
- **Isolation is the tool list, not a flag**. A child is an ordinary `Agent` built with `SUBAGENT_TOOLS` = `read`, `glob`, `grep`, `recall`. It holds no `write`, `edit`, `bash`, `remember`, `ask`, `plan`, `todo`, or `delegate`, so there is nothing for it to be talked into using - verified from outside the process by the mock provider logging the tools each request was offered. `bash` is excluded even though a gated read-only command would be permitted, because a child has no approval channel and is refused every gated tool anyway; including it would only teach the model to try. A child's `systemPrompt` replaces the parent's, since the parent's rules are about a conversation with a person and a child has no user to ask.
- **Failures are never silent**. A child that dies is a line of its own in the parent's report, naming the reason; the rest of the batch still reports. A child that ran out of turns or budget is `stalled`, not `completed` - claiming a clean finish on partial work is how a parent ends up trusting a truncated report. A child stopped by Ctrl+C is `interrupted`. The transcript keeps one row per delegation: it opens with `delegating…`, counts `delegating N of M` while the batch runs, and settles to `delegated N tasks · reported` (or names what did not finish) **in place**, where the work started.
- **No wall-clock timeout.** A cap kills legitimate long work - a deep review needs minutes and keeps making progress throughout. Staleness measures *silence* from the last sign of life: 450s idle, 1 200s in-tool (a long grep or fetch is also silent, so the in-tool figure is the larger one). It is enforced by aborting the child, not by refusing to wait, or a wedged request would hold the parent's turn open until the session's own ceiling. The child gets its own `AbortController` that the turn's cancellation is relayed into, so Ctrl+C still reaches everything and a runaway child can be cut loose on its own account.
- **Caps are refused, never applied silently.** `maxPerTurn` (8) and `maxConcurrent` (4) are checked before anything spawns; a batch that would exceed the turn's remaining budget is an error naming both numbers, because a batch quietly cut to four is four tasks the model believes are running and are not. `maxPerTurn` resets with each turn - a session-wide counter would have the third turn refused for children the first two spawned. The count is spent across calls in a turn, not per call.
- **The panel reads data, not prose.** The tool hands its children over as an `AgentEvent` (`{ type: "subagents" }`) after the call, the same contract `snapshot()` gives the plan tools, so the dock and `/agents` draw the runner's own state rather than parsing a sentence for a model name. A dock row is `◐ goal · model · N tools · 4s`, capped at two rows with `+N more · /agents for the roster`. The registry is scoped to the call in flight, so a second delegation's count cannot include the first's children, and bounded at twelve with oldest-settled-first eviction - a child in flight is never the thing that disappears.
- **`/help` no longer enumerates the commands.** Adding one command pushed the block past a 24-row terminal and scrolled the keymap off the top: it was already thirteen rows, seven of them a run-on list of names the palette renders better. It now names the count and points at `/`.
- **Runner is shared**. `childRunner` lives in `subagent.ts`, not `app.ts`, because `kicode -p "…"` is a supported way to run and delegation silently missing from one of the two doors is worse than missing from neither.
- **Outcome**: typecheck clean; 1 314 tests across 56 files; end-to-end against the mock provider - two children spawned in parallel, both reported, the parent read both reports, exit 0; `MOCK_LOG=1` shows children offered `read, glob, grep, recall` and the parent the full set plus `delegate`.
- **Known gap**: a child's tokens are carried on its `SubagentResult` and shown in the report, but are **not** charged to the parent's ledger, so `/context` and `/usage` under-report a session that delegated. A child is a separate `Agent`; folding its spending in needs a seam from the tool back through the loop into the session's budget, which does not exist yet. The fix is to give `Agent` an `absorb(other)` and have the loop charge each settled child on the `subagents` event.

## ADR-054: Named Subagents With a Grantable Permission
- **Context**: ADR-053 gave every child the same model and the same instructions, and refused a role enum plus a per-role model as a settings surface nobody gets right. The owner asked for named agents anyway — `cody-git` for GitHub work, `cody-frontend` for the front end — and for the permission to grant edit access to be a choice, made from the UI. That is a direct override of the earlier call, and the override is right: the reason against roles was that a role enum *plus* a per-role model *plus* a role picker is a lot of surface, not that naming a child is wrong. One profile — a name, a line of description, a specialisation, an optional model, a permission level — is the whole of it.
- **Decision**. `delegate` gains an optional `agent` field naming a profile. The names and their descriptions go **into the tool description and as a parameter enum**, because that string is the only place a model learns `cody-git` exists; an `agent` parameter with nothing beside it is an invitation to guess. A profile is chosen per task, so one batch can send one task to `cody-git` and another to `cody-frontend`.
- **Two files, one format**: `<home>/.kicode/agents.json` and `<cwd>/.kicode/agents.json`, the project's overriding by name. Deliberately **not** an `agents` block in `kicode.json`: that file is committed, so a modal editing it would be rewriting a tracked file behind the user's back, and the two would then disagree about who owns an agent. An override replaces rather than merges, so a project can *narrow* a global agent's permissions as well as widen them.
- **`bash` is never grantable, at either level.** Read and edit are the file-shaped permissions. A shell is arbitrary code and a child has no approval channel to ask about it, so a grantable `bash` would mean a model you delegated to can run anything, unsupervised, four at a time — and unlike a write, there is no diff to show the user first. Edit is opt-in per agent and off by default; a child with it says so in its prompt. Nothing else is grantable either: no `remember` (two agents racing on one brain) and no nested `delegate` (the tree stays flat).
- **Everything a profile decides is resolved once**, in the tool holding the profile, and handed to the child builder as arguments (`model`, `tools`, `instructions`). Re-deriving it in `run.ts` would be a second place for the permission grant to be re-read — and the grant is the one thing in this feature that must not be read twice.
- **An unknown name is refused, and the error lists the real ones.** Falling back to a general-purpose child would be a substitution the model never asked for and would not know about, so it would report a general-purpose result as the specialist it never ran. A batch naming one bad agent is refused whole rather than half-run.
- **The editor is a form, not a wizard.** `/agents` lists what is defined plus a `＋ New agent`; opening one gives a card with Name, For, How it works, Model, May edit files, Where, and Save (and Delete on an existing one). Only the field under the cursor carries a hint line — every field carrying one would double the height, and a form that has to scroll to reach its own Save button is a worse form. `↑↓` moves, `enter` edits a text field or flips a toggle, `‹›` also flips, `esc` steps out of a field and then closes. Clicks go through the same handlers as keys, so the two cannot diverge. **Name, For and Model are one line each** and are committed as their first line, because this is the prompt's editor and `enter` inserts a newline — a name that failed validation over a stray newline would be a confusing message about characters. The form is a scratch pad until Save, so `esc` discards nothing.
- **`/agents running` is the live roster**, from the same registry the dock draws. `/agents` used to be that, and managing definitions without a way to watch the children would have been a worse trade.
- **Outcome**: 1374 tests across 57 files; typecheck clean; verified end to end against the mock — a project-scoped `cody-frontend` with write permission resolved from `.kicode/agents.json` and the child was offered `read, glob, grep, recall, write, edit`, never `bash`.

## ADR-056: Enter Is "Next Field", Everywhere; The Card Is Sized From What a Row Renders
- **Context**: two complaints about the subagent editor. The card was *squeezing* — `Where`'s value ran past the card's right edge and the highlight smeared off into the page — and filling the form was ceremony, because a text field took Escape to leave and Enter only opened it.
- **Decision, the squeeze.** The card's width was measured from `field.value`, but a **toggle renders both of its options**: `Where` is worth `all projects` and draws `[all projects] / this project`. One `formValueText` now says what a row shows and both the width measurement and the row drawing read it, so they cannot disagree — which is the same reason `MenuPanel.descriptionWidth` exists. `formValueText` deliberately does *not* include the caret: the row places it, and a value that already carried one was drawn with two. A test now asserts there is exactly one.
- **Decision, Enter.** **`enter` is "next field" on every kind of field.** It commits what is typed and steps to the next one, *already open for typing*, so filling the form is type, Enter, type. It was previously "open this field" on a text field and "flip this toggle" on a toggle — the same key meaning two things depending on where the cursor sat, and `Where` would have silently changed scope on a stray Enter. Toggles now change with `‹›` or space, and the footer says so. A line break is the *other* key: shift+enter arrives as `newline` and falls through to the editor, which is why `How it works` holds a paragraph and the others cannot.
- **Consequence, stated because it is a real limit**: `↑↓` do not move between fields *while a field is being typed into*, because a text field needs them. Reaching `Save` from a text field means pressing Enter until you pass a toggle — and a toggle does not open for typing, so the arrows work again from there.
- **Subagents joined the settings panel's `Shortcuts` group** (ADR-051's pattern): a door, not a value, running the same call `/agents` makes. It is the eighth row, which pushes the first value rows below the fold on a twenty-four-row terminal — the panel already scrolls with the cursor, and the settings test now asserts that scrolling rather than assuming the values are on screen at open.
- **Outcome**: 1384 tests across 57 files; typecheck clean; build 347.92 KB. New tests: every row stays inside the card including both toggle options, one caret and not two, Enter steps to the next field with its value, a full fill-then-save carries every field through to the file, Enter steps *past* a toggle without changing it, and the Subagents door opens the same screen `/agents` does.

## ADR-055: The Editor Draws the Live Buffer, Not the Saved Value
- **Context**: the subagent editor shipped unusable — you could open it, get a caret, and type, and nothing appeared. The row was drawn from the field's *committed* value while the keys were going into the shared `LineEditor`, so the text was there and the screen was not. It reads as a dead keyboard, and nothing on screen said otherwise.
- **Decision**. A `FormField` gained an optional `caret`, and the panel renders `value.slice(0, caret) + "▌" + value.slice(caret)` — the live line, caret where the cursor is rather than at the end of the row. `agentForm()` reads the editor while a field is being edited and points the row at it. The `(empty)` placeholder is suppressed on the row being typed into, because `(empty)` beside a live caret reads as a value rather than as a hint. Only the line the caret is on is drawn: the buffer takes paragraphs (this is the prompt's editor, so Enter is a newline), and putting a paragraph in one row would break the card's width.
- **The prompt box is hidden while the form is up.** Two editors drawing the same buffer on one screen is not a form, it is a puzzle. `boxShown` now counts `state.form`.
- **The footer names what Enter does, per field.** `How it works` takes paragraphs, so `enter new line`; every other field is one line and there is no key to name.
- **Outcome**: 1379 tests across 57 files; typecheck clean; four new tests — typed text appears, the caret sits at the edit rather than the end, the placeholder stays off the edited row, and only the caret's line is drawn. A fifth pins the *cause* of a bug this round could have shipped: `agentFieldKey()` read the field key out of the rendered panel, and the panel's footer called `agentFieldKey()` — a cycle that blew the stack, made `draw()` throw, and left the screen on its last good frame. Nothing in the failure named the cycle, and every symptom pointed at the keyboard instead. The fix is a module-level `AGENT_FIELD_KEYS`, the one source for the panel, the cursor and the handler.
